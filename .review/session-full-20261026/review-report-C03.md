### [MEDIUM] Finding 1: SOI rebase produces surface/atmosphere-intersecting conics with no re-check — debris decay and vessel impact are lost after a transition
**File**: crates/csp-sim/src/lib.rs:8504 (apply_soi_transition), :5064 (schedule_debris_decay), :6206 (apply_to_rails_at)
**Problem**: `apply_to_rails_at` refuses to stamp any conic whose periapsis does not clear `radius + max(atm_top, bubble_radius)` (:6271-6281) — "an orbit that intersects the planet has no rails reading… the vessel would orbit through the atmosphere untouched forever" — and `schedule_debris_decay` is likewise only ever called from that one site (:6323 is its sole caller). But `apply_soi_transition` (:8560-8564) writes the rebased conic from `PatchedConics::rebase` with **no clearance check and no decay rescheduling** (rebase itself validates only structure, not geometry).
**Evidence**: `grep -n schedule_debris_decay lib.rs` → exactly two hits: definition :5064, call :6323. `apply_soi_transition` body :8504-8571: rebase → write state → contract_notify → return; the follow-up `schedule_next_soi` only publishes SOI crossings.
**Impact**: (a) A debris fragment entering a child body's SOI on a periapsis-below-`h_top` conic never gets a `DebrisDecay` event and orbits through the body forever — violating PLAN §3.5 "Debris with periapsis below `h_top` decays on a scheduled `DebrisDecay` event" (bounded only by the 64-debris cap eviction, which itself only runs while the bubble is ticking). (b) Any vessel (crewed included) rebased onto a sub-surface trajectory — the classic under-adjusted Mun transfer — ghosts through the body on rails with no drag, no crash, and no auto-demote; the exact situation the stamp-time gate exists to make impossible is reintroduced by the rebase path. Common in play (first flybys aim close).
**Suggestion**: In `apply_soi_transition` after the rebase: if the new conic's periapsis fails the same floor test, either (i) for debris, delete/schedule `DebrisDecay` at next periapsis (reuse `schedule_debris_decay`), and (ii) for vessels, schedule a materialization/degradation event (`SoiRescan` is the wrong tool; a new `AtmosphereEntry`/impact-proximity `Clamping` event matches §2.6.5's intent) or at minimum refuse-and-degrade like the stamp path does. Minimum viable fix: call `schedule_debris_decay` for debris after every rebase.

### [MEDIUM] Finding 2: A completed ascent autopilot permanently suppresses auto-rails — orbit is never shown in the map until the player manually disengages
**File**: crates/csp-sim/src/lib.rs:4802 (detection exclusion); crates/csp-ai/src/lib.rs:162-165 (phase 4)
**Problem**: The auto bubble→rails detection skips any vessel with an engaged autopilot (`if self.autopilots.get(vid).is_some_and(|a| a.enabled) { continue; }`), justified by "its circularization commands could never issue". But the ascent autopilot's terminal phase 4 is "Done — drift until disengaged": it issues only `set_throttle(0.0)` forever and never disengages (the frozen `ControlApi` has no disengage verb, and `DisengageAutopilot` is a UI-only command).
**Evidence**: csp-ai/src/lib.rs:162-165 — `_ => { api.set_throttle(0.0); }` with the doc "the record stays until `DisengageAutopilot`". lib.rs:4794-4803 — the exclusion is unconditional on `enabled`.
**Impact**: On the autopilot launch path — the path the tutorial/Program panel pushes players onto — the craft reaches a clean orbit and then stays `InBubble` indefinitely: no conic, so the map draws no orbit line, `SetManeuver` (requires on-rails) rejects, transfer planning is unavailable, and every frame pays full bubble-tick physics instead of a rails jump. The disengage button exists (csp-ui/program.rs:1630) but nothing surfaces that it is now *required*; players will read "I got to space but the game says I'm not in orbit". The manual-flight path (cut throttle, periapsis clears 70 km) works — verified by the two passing `auto_rails_*` tests — so this is specifically theautopilot-completion hole.
**Suggestion**: Either (a) csp-ai: phase 4 marks the program complete in `state.persist` and the sim treats a completed program as passive (the exclusion checks a `persist["phase"] == 4`-equivalent signal the driver exposes), or (b) simplest: the autopilot stops re-issuing `set_throttle(0.0)` in phase 4 (idle → no control intent) and the exclusion is narrowed from "record enabled" to "record issued a command in the last N ticks". Cross-cluster: the fix spans C26 (csp-ai) and this line; flagging here because the exclusion predicate is in-range.

### [MEDIUM] Finding 3: `step_bubble_range` is a 915-line god-function with two duplicated debris-retirement blocks (DRY/CRAP)
**File**: crates/csp-sim/src/lib.rs:3987-4901
**Problem**: One function carries: per-tick drain+control, per-tick aero refresh, the two-pass propellant plan/debit, the physics batch build/step/write-back, structural/thermal/reliability evaluation, latch transitions, notification/tech side-effects, impact/breakup consequences, oldest-debris eviction, docking latch/lifecycle passes, and the auto-rails detection — under `#[allow(too_many_lines, too_many_arguments, cognitive_complexity)]` with 11 loop-local accumulators (`dead_vessels`, `latched_total`, `impacts`, `burns_done`, `rail_break`, `failures`, `impacted`, `latched_now`, `rel_post`, `rel_burns`, `rel_rebody`).
**Evidence**: The impact-removal block :4540-4608 and the max-debris eviction block :4650-4692 are ~90% identical (debug_assert heap scan → `drop_vessel_projects` → burn-exit credit loop → `lose_aboard_crew` → `aero.remove` → `dead_vessels.push`); any future edit to retirement semantics (e.g. Finding 1's decay fix) must be made twice. Same duplication class: `remove_vessel` :4997-5046 repeats the retirement a third time for the event-driven path.
**Impact**: PLAN §8.6 mandates CRAP/complexity gates; this function is the sim's highest-churn hot spot (three bug-fix commits in the last five landed here) and every new subsystem phase grows it further. Review and bisect cost are already high.
**Suggestion**: Extract, under the existing borrow-split: (1) `retire_debris_vessel(vessels, physics, vid, t, rel_burns, dead_vessels, shadow)` unifying the three retirement sites (the heap-scrub difference is assert-only); (2) `tick_consequences(...)` for the failures/impacted/eviction pass; (3) `detect_auto_rails_candidates(vessels, physics, t) -> Vec<VesselId>` for :4778-4829; (4) `tick_propellant_pass(...)` for :4141-4268. Each phase boundary already has a documenting comment — the seams exist.

### [LOW] Finding 4: Tracked opt-in promotes only `SoiTransition` to Clamping — §2.6.5's per-object promotion is narrower than spec
**File**: crates/csp-sim/src/lib.rs:5304-5316; crates/csp-sim/src/events.rs:449 (class_of)
**Problem**: §2.6.5: "Per-object opt-in ('track this vessel') promotes that object's events `Silent → Clamping`." `class_of` treats only `SoiTransition` as track-sensitive; the `SetVesselTracked` heap rewrite (:5308-5315) correspondingly rewrites only `SoiTransition` entries. A tracked vessel's `DebrisDecay` and `PartFailure` stay `Silent` forever.
**Evidence**: events.rs:449-477 — the only `tracked.contains` check is in the `SoiTransition` arm; `PartFailure`/`DebrisDecay` sit in the fixed-`Silent` arm with a comment declaring the design choice for `PartFailure` (surfacing rides the notification log — defensible), but `DebrisDecay` of a tracked vessel gets no such rationale.
**Impact**: Warp is not demoted when a player-tracked object's debris decays. Marginal in practice (players rarely track debris), and the load-bearing member (`SoiTransition`) is correctly promoted; noting as a spec-text deviation, not a playability break.
**Suggestion**: Either extend the promotion to `DebrisDecay` (one arm in `class_of` + one match arm in the rewrite), or record the deviation in events.rs's module doc next to the `PartFailure` rationale.

### [LOW] Finding 5: Duplicated occupancy scans and repeated heap-scrub idiom in range
**File**: crates/csp-sim/src/lib.rs:5888-5936 vs :5954-5990; :3933, :5041, :6588, :6830
**Problem**: `spawn_site_occupied_by` and `spawn_site_occupant` are two ~40-line copies of the same InBubble/re-materialized-latched overlap loop differing only in `bool` vs `Option<VesselId>` return. The `shadow_events_whole` → `mem::take` → `filter(event_names_vessel)` → `collect` scrub idiom appears four more times across residence transitions (:3933, :5041, :6588, :6830).
**Impact**: The occupancy pair is the exact shape that diverges — a future fix to the latched-pose rebuild (e.g. the `pose.body != dominant` skip at :5909) applied to one copy silently misses the other; the launch path uses one and the pre-flight check the other.
**Suggestion**: `fn site_overlaps(&self, candidate: &WeldedBody) -> impl Iterator<Item = VesselId>` with both public helpers as folds over it; `fn scrub_vessel_events(&mut self, vessel, shadow)` for the heap idiom.
