# PRD-10 — csp-phys II: weld, aero, thermal, structural, session review

**Cluster files:** `crates/csp-phys/src/{weld 1577, aero 2033, merge 865, thermal 831, structural 544, readout 706, graph 355, hull 370, profile 402, session 3204}.rs` + `crates/csp-phys/tests/{session 244, resolve_parts 267}.rs`.

**PRD baseline:** §2.4 (weld Stage 1 pure/bit-identical; breakup with defined momentum tolerances; children inherit aero tables; dock-merge → one body), §2.4.1 (isotropic voxels ≤4 M budget, 66-direction geodesic + barycentric, per-`ConfigMask` tables, `Cm_α` ≤5% of direct), M3 row (snap graph, staging, scale+variants, Δv/TWR, `MissionProfile` stub, craft files with stable ids), M4b/M4c/M6 exit rows.

**Verdict:** the physics half of this cluster is strong — weld Stage 1 is genuinely pure, permutation-bit-identical, and heavily validated; the aero table is deterministic with a non-tautological `Cm_α` check; breakup conserves momentum to the plan's stated tolerances and the sim stamps fragments the same way. **`CraftSession` is also a careful, well-tested attach-graph — but the two user complaints are real and traceable to model-level semantics**: subtree-only removal + root immovability + zero undo make the VAB destructively rigid, and a few smaller attach-validation gaps (double-binding, no overlap check, unbounded `surf:` ids) sit below the UI planner's guardrails. PRD-11 covers the same complaints at the pointer/render layer; this report holds the model layer.

## Findings

### HIGH

**H1 — There is no undo anywhere; `remove_part` on the root wipes the craft with no recovery.**
`session.rs:1304-1316` (`remove_part` = node + whole subtree; root removal empties the session), returns only `Vec<PartNodeId>` — the removed `SessionNode` records are dropped, so even a hypothetical undo can't restore ids/edges/stages without a full clone. `CraftSession` keeps no history; `VabAction` has no Undo/Redo variant (`csp-ui/src/vab.rs:152-259`); repo-wide grep for `undo|Undo|history` finds nothing in csp-ui/csp-view/csp-app. The UI binds three *instant* delete gestures (right-click, Del/Backspace, drag-to-palette — PRD-11 H2). Impact: a stray remove on the root pod deletes the entire rocket permanently — the user's "no undo" complaint is a model-level absence, not just a missing keybind. Suggestion: since all mutations flow through `VabSession::apply`, snapshot the session (or a compact op-inverse journal) onto a bounded undo stack before each mutating arm; `CraftSession: Clone` makes the cheap version ~20 lines. Also consider `remove_part` returning the removed records (or an explicit `detach_subtree`) so "lift out + re-place" and undo are possible.

**H2 — The root is immovable and no whole-craft reposition reaches the player — the session half of "can't move the rocket".**
`reattach` refuses every root move: `is_ancestor_of(nodes, id, edge.parent)` (session.rs:1333) is always true for the root since every chain tops at it — surfaced as `WouldCycle` ("would cycle the tree"), a misleading message for what is really "root is the anchor". `reroot` (`:1364-1436`) deliberately preserves all body poses bit-identically — it flips tree direction, it does **not** move the craft. The one op that *could* translate the whole stack — `set_transform` on the root (`:1441-1455`) — has **zero call sites** in csp-ui/csp-view/csp-app/csp-server (grep verified); it's test-only API surface. Compound with H1: after removing a mid part, the subtree below is gone, and if the remainder is root-only or root-anchored, nothing in the model or UI can reposition it — the "glued to the ground" read. (PRD-11 H3 documents the UI-side dead drag + refusal spam.) Suggestion: expose a root-translate op (`VabAction::Translate`/`Move`) through `set_transform` — the model already supports it — or let root Grab lift the whole craft and re-anchor on drop; give `reattach`-on-root a dedicated typed error so UI/agents don't see a bogus cycle refusal.

**H3 — `remove_part` is subtree-delete only: no detach, no reparent-to-grandparent, no subassembly.**
`session.rs:1300-1316` — "a node cannot outlive its parent edge" is the only removal semantic; removing a mid-stack tank silently deletes the engine/decoupler stack beneath it (confirmation line only; `vab.rs:996-1013`). The Grab lift is presentation-only (`vab.rs:1079` "the node keeps its edge until the drop rewrites it") — a subtree can never be set aside, duplicated, or saved as a subassembly. KSP parity would keep subtree-pickup but offer delete-this-part (children promote to the parent) or at least warn before a large subtree vaporizes. Impact: amplifies H1 — one removal can take the whole lower stack with no undo; also blocks the natural "slide a part underneath" workflow that would work around H2. Suggestion: add `remove_part` variants — `remove_and_reparent` (children re-edge to the removed node's parent, resnapped) — and/or a minimum confirmation when `removed.len() > 1`; both are cheap on top of `subtree_ids`/`compute_attach`.

### MEDIUM

**M1 — One-attach-node-many-children is unenforced in the model; double-binding welds into coincident parts.**
`bound_attach_nodes` (session.rs:1056-1067) exists, and its doc says "`add_part`/`reattach` do not consult this: an explicit `AttachEdge` stays the caller's responsibility" (`:1053-1055`). Every *UI* planner respects it (`vab.rs:1761`, `:1256`, `:1300`), but the session ops accept an edge onto an already-mated node — two children then snap to the identical point, producing coincident/interpenetrating colliders that `weld` happily consumes (topology+transform is all the weld needs). `validate` (`:1788-1829`) checks binding *existence* and post-scale diameters but never occupancy — a double-bound craft validates launchable. Reachable by any non-VAB writer: MCP `craft.build`/`editor.build` tools, bench scenarios, the §2.11 design solver, or a crafted file. Impact: silent geometric corruption on any path that skips the planner. Suggestion: enforce one-child-per-`(parent, parent_node)` inside `add_part`/`reattach` as a typed error (or at least a `SessionWarning::AttachNodeOccupied` in `validate`); the tree invariant is already the model's job.

**M2 — `validate` performs no geometric overlap check.**
`session.rs:1748-1832` — errors cover empty/missing defs/bad `built`/bad bindings/stage caps; warnings cover staging and diameter drift; nothing detects two parts whose scaled colliders intersect (via M1's double-bind, or `set_transform` free-placement, or a `surf:` mount inside the parent's hull). `set_transform` (`:1441-1455`) only gates `is_valid` — any finite pose is legal. Impact: physically impossible craft launch with overlapping parts; also hides planner bugs (PRD-11 M3 is the UI-side note). Suggestion: a cheap AABB-overlap warning in `validate` using the same per-node hull AABBs the weld already computes (`build_thermal_net`'s `aabbs`, weld.rs:606-654) — exact enough for a warning tier.

**M3 — `joint_loads` evaluates the joint about the part origin, not the attach node — a systematic torque-arm error.**
`structural.rs:210` — `p_j = transforms[id].offset` is the child's *origin* in body frame; the doc calls it "the node's body-frame attach point" (`:23-26`) but the real attach node sits at ±half-height from the origin (e.g., a 2 m tank's joint is ~1 m from its origin). `PartGraph` carries no attach-node ids (editor metadata — `session.rs:1721-1723` "do not enter the weld input"), so the true point is unrecoverable at this layer. `F_J` is unaffected (forces don't need a point), but `τ_J` and `point_accel(p_j)` are evaluated about the wrong point — torque readings are systematically off by the subtree-moment difference between origin and true joint. Impact: joints break later/earlier than authored `max_torque_nm` warrants — largest on long tanks, which is the common stack. Suggestion: record the joint point at attach time — the session *knows* the snapped node position (`snap_transform`'s `p_p`); carrying a `joint_point_m` on `PartNode` (or into `WeldPart`) makes the joint-load point exact and also fixes the same ambiguity in the thermal net's contact-face heuristic.

**M4 — The 1e-6 attach-diameter tolerance makes pre-scaled placement impossible; attach-then-rescale bypasses the same rule.**
`ATTACH_DIAMETER_REL_TOLERANCE = 1e-6` (session.rs:151) — the §3.1 adapter rule implemented as *exact match to f64 noise*. Two authored size classes exist in `data/parts` (0.625 pod top vs 1.25 elsewhere) and the Continuous-scaled tanks (0.5–2.0× → 0.625–2.5 m node diameters). A tank pre-scaled to 1.5× (1.875 m node) matches **nothing** — no authored or scaled node can equal an arbitrary scaled diameter — so `add_part`/`reattach` refuses it everywhere. The only legal path to a scaled craft is attach-at-stock then `set_scale`/`set_stretch`, which `resnap_self_and_children` (`:1504-1509`) performs *without* the diameter gate (it's "a placement rule"), leaving a permanent `AttachDiameterMismatch` warning and a geometrically gapped joint that welds anyway. Impact: the gate and the post-scale path disagree about what's legal — the strict check buys nothing except making pre-scaled placement dead, while the warned workaround produces exactly the mismatch the gate exists to prevent. Suggestion: pick one semantic — either widen the gate to "same authored size-class band" (tolerance ~5–10% so scaled-into-class still counts) or apply the diameter check in `resnap` too and refuse post-scale mismatches; as-is the rule is simultaneously too tight and unenforced.

### LOW

- **L1 — `surf:` namespace collides with authored node ids; decode shadows real nodes.** `scaled_attach_node` (session.rs:773-784) checks `decode_surface_node` *before* the def's authored nodes — an authored `AttachNode` literally named `surf:<x>:<y>:<z>:<nx>:<ny>:<nz>:<d>` parses as a surface mount and shadows the authored record. The data validator (`csp-data/src/validate.rs:2671-2714`) doesn't reserve the prefix. Relatedly, `validate`'s `node_known` (`session.rs:1796-1799`) treats any well-formed `surf:` string as known — a crafted file can name arbitrary surface points and never trip `UnknownAttachNode`. Suggestion: reserve the prefix in the def validator, and have `scaled_attach_node` prefer authored nodes when the id matches one verbatim.
- **L2 — `decode_surface_node` accepts unbounded geometry.** Only finiteness and `diameter > 0` are checked (`session.rs:737-756`) — `surf:1e300:…` decodes, and `compute_attach` then builds a finite 1e300 m offset that passes `is_valid`; `validate` agrees it's a known node. A crafted file can place parts at astronomical offsets and launch. Suggestion: bound decoded `position_m`/`direction` norms to plausible part scales (e.g., ≤ a few hundred m) or to the parent def's `size_m` envelope.
- **L3 — Stale doc on `surf:` encoding.** `session.rs:696-700` claims stored values "are already at the node's built scale+stretch, so decode applies no further scaling" — directly contradicted by `surface_node_id`'s doc (`:704-709`, def-local) and by `scaled_attach_node`, which *does* scale (`:775-784`). Behavior is correct; the comment describes a dead design. (Also flagged as PRD-11 L2.)
- **L4 — `reattach` on the root reports `WouldCycle`.** The error text "attaching X under Y would cycle the tree" (session.rs:408-411) is what programmatic callers and agent tools see for a root move — misleading; a `RootImmovable` variant (or doc'd grab-level refusal) reads better. Trivial.
- **L5 — Repeated O(n) scans compound: `children_ids` per node.** `children_ids` is O(n) (`:1040-1046`); `subtree_ids` calls it per popped node → O(n·depth); `validate_staging` calls it per decoupler; `bound_attach_nodes` rebuilds it per call. Fine at the 300-part VAB criterion; at M6's 1000-part station / per-frame VAB planning it becomes the avoidable part of the latency budget. Suggestion: build the children index once per op (the `body_transforms` pattern at `:1095-1100` already does this).
- **L6 — `WeldedBody.aero` is `#[serde(skip)]` + unhashed, per §2.4.1 — but nothing in this crate guarantees a re-derive exists.** Correct per the plan ("never serialized… re-derived on load"), and `build_aero_tables` is the deterministic path. Flagged only as a cross-cluster dependency: exploration map notes `InstallAeroTables` is never issued and the sim computes tables itself (fallback at `csp-sim/lib.rs:5529`); if that fallback ever misses, `body.aero == None` silently drops drag/heating — no assertion guards "tables installed before atmosphere flight" in csp-phys. Verify in PRD-03/09 whether the §2.4 "refuses to enter atmosphere-bearing flight without them" refusal exists anywhere.
- **L7 — `remove_stage`/`insert_stage` leave crafted out-of-cap stages untouched (consistent, but silent).** `remove_stage(at)` shifts `> at` down — a crafted stage 5000 shifts to 4999 and stays illegal only via `validate`. Harmless; noted for completeness (`session.rs:1690-1698`).
- **L8 — `empty active` aero build returns `ref_len_m = 1.0` placeholder** (`aero.rs:1309`) — fine, but `ref_area_m2 = 0` means `force_torque_body` on that table returns nothing; combined with L6 this is the silent-no-drag path again.
- **L9 — `insert_stage`'s refusal condition is redundant** (`session.rs:1669-1678`): `n.stage >= at && n.stage == MAX_STAGE_INDEX` ≡ `n.stage == MAX` since `at ≤ MAX` is already gated. Correct refusal, dead sub-expression — tidy only.
