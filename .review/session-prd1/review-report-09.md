# PRD-09 Review — csp-phys I: integration + contact + part resolution

**Cluster:** `crates/csp-phys/src/{simple.rs (4197), resolve.rs (3611), part.rs (440), backend.rs (199), tensor.rs (324), lib.rs (145)}`, with the sim-side joint lifecycle (`csp-sim/src/joints.rs`, 1248) and the bubble-step call sites (`csp-sim/src/lib.rs`) read for context.

**Method:** read every non-test line of the six files; traced the `PhysicsBackend::step` pipeline (force → integrate → ground/pair/joint generation → PGS velocity → Baumgarte position → settle latch); cross-checked the joint/island model end-to-end (`JointDef` → `JointConstraint` → `joints::batch_joint_defs`/`latch_pass`/`lifecycle`/`apply_latch`/`merge_graphs`); audited resolver consumers for stat divergence (VAB `analyze`, `resolve_built`, flight `CraftDef`, `ReliabilitySpec`); verified `aero == None` reachability through `aero_tables_stale`/`ensure_aero` and the spawn install path.

---

## 1. Headline findings

1. **The backend is solid — no High-severity defects in this cluster.** The integrator, contact solver, joint rows, and resolver are unusually careful code: fixed iteration orders, cold-started PGS, position-level Baumgarte with a reasoned deviation from velocity-bias, Coulomb-disc (not per-axis) friction projection, speculative anti-tunneling on both manifolds, per-tick correction caps, rotating-frame settle gates, and a heavily gated typed-error resolver. Bitwise determinism is asserted by tests throughout.
2. **`WeldedBody.aero == None` in atmosphere does NOT mean "no drag" — it means a *different* drag model.** The `None` arm of `accumulate_forces` applies the M2 placeholder (velocity-aligned AABB cross-section × `env.drag_cd`), silently. PLAN §2.4's rule is *refusal* ("refuses to enter atmosphere-bearing flight without them"); the sim makes it unreachable in shipped flow (spawn installs tables, `ensure_aero` heals per tick), but `SimpleBackend` is the public backend trait — any body without tables quietly flies on placeholder physics.
3. **Joint constraint impulses are invisible to the structural load model.** `solve_joint_rows` applies real impulses to both bodies but writes no `Contact` record, so `external_loads`/`joint_loads` never see soft-capture forces. A capture island under thrust carries unbounded joint load with zero structural consequence — the only separation path is window expiry.
4. **The joint/island model works.** Soft-capture is a bilateral 3-row compliant constraint in the same PGS pass; momentum conserved by construction; latched sides are static; the latch merge applies §2.9's hand-off (`v = p_total/m_total`, `ω = I⁻¹L`); undock splits via the breakup path; the 16-cap degrades to clean separation with a logged Recoverable. `RapierBackend` genuinely does not exist (`impl PhysicsBackend` has exactly one impl; rapier is workspace-pinned but dependency-less) — the deviation is documented in three places (`backend.rs:49-58`, `lib.rs:55-59`, `joints.rs:14-18`).
5. **Docking is unreachable — confirmed.** The entire pipeline (port specs on `WeldPart`, capture predicate, reel-in, `DockSeam`, merge bookkeeping, undock) is complete sim-side, but **no `DockPort` module exists in `data/parts/`** (11 part files, zero `DockPort`), so `world_ports` returns `[]` for every real vessel forever.
6. **Resolver is the single source of truth — verified.** `EffectivePart::weld_input` is the only producer of `WeldPart`; editor (`readout.rs:157`), flight (`csp-view/src/lib.rs:2082-2086`), and inspector (`csp-ui/src/vab.rs:1684`) all read the same projection. `weld_input` is provably qual/wear-independent — consumers cannot disagree on physics stats. The only divergence is a *documented* display one (editor resolves at `FRESH` qualification; the sim re-evaluates the live curve via `ReliabilitySpec.qualification_curve`).

## 2. Defects and gaps

### D1 — `aero == None` silently substitutes the placeholder drag model in atmosphere *(spec deviation; Low-Medium)*

- **Where:** `crates/csp-phys/src/simple.rs:1546-1564` (`accumulate_forces` `match &b.aero { … None => placeholder }`), `:1390-1421` (`external_loads` `None` arm distributes placeholder by mass share).
- **Problem:** PLAN §2.4 (PLAN.md:297-298): *"The sim refuses to launch a craft whose Stage-2 tables for ConfigMask::default() are not installed, and refuses to enter atmosphere-bearing flight without them."* The `None` arm instead applies `F = −½ρ·drag_cd·A_aabb·v²` — the documented M2 placeholder — with no error, no warning, no event.
- **Evidence:** In the shipped sim the arm is unreachable: spawn installs `ConfigMask::ALL` tables whenever `env.atmosphere.is_some()` (`csp-sim/src/lib.rs:5524-5539`), `aero_tables_stale` treats `aero: None` as stale (`lib.rs:10136-10146`), and the per-tick pre-pass re-attaches before integration (`lib.rs:3742-3751`). But `SimpleBackend` is a public `PhysicsBackend` — bench scenarios, hand-authored `WeldedBody`s, `csp-script`, or any future path that skips the sim's aero bookkeeping flies silently on the wrong model. The placeholder uses the *environment-level* `env.drag_cd` constant and a velocity-aligned AABB area that over-estimates for attitudes — physically different answers with zero signal.
- **Impact:** Silent wrong physics on any code path that reaches `step` with `atmosphere.is_some()` and `body.aero.is_none()`. In-shipped-flow unreachable today; a latent trap for the exact class of second-source consumers (MCP `sim.command`, scripts, bench) that the exploration map shows are the *only* producers of much of the surface area.
- **Suggestion:** Either (a) make the `None` arm unreachable — return a typed error or `debug_assert` + zero-force with a `Recoverable`-grade notification through the sim's `degraded` channel, matching §2.4's refusal; or (b) keep the placeholder but surface it (one-shot degraded error per vessel per graph change) so a table-less atmosphere flight is visible rather than silent. At minimum, document at the `PhysicsBackend` trait level that `aero == None` is *not* a legal in-atmosphere state, since the spec-level refusal lives above the backend and the fallback lives below it — the split is where the trap sits.

### D2 — Soft-capture joint impulses never reach `external_loads` — no stress across joints *(gap; Low)*

- **Where:** `crates/csp-phys/src/simple.rs:2095-2138` (`solve_joint_rows` applies `apply_two_body_impulse` but there is no impulse write-back — compare the contact write-back at `:2464-2483`); `:1444-1462` (`external_loads` attributes only `Contact::impulse` records: ground + pair).
- **Problem:** The flagged question "stress across joints" has the answer *none exists*. The joint rows apply real two-body impulses, but they leave no record: `JointConstraint` has no `Contact` channel, and `external_loads` cannot see them. The §2.4 breakup model evaluates per-part external forces per tick — a soft-captured vessel under thrust carries the full joint reaction load, but nothing attributes it to the port node or its structural limits.
- **Evidence:** The joint solve has no write-back block (the pair loop at `:2476-2483` has one; the joint call at `:2091` has none). `csp-sim` reads `external_loads` for `joint_loads`/`failed_joints` every tick (`lib.rs:3954-3990`) — a port attachment can never fail from capture loads. Separation only happens at window expiry (`joints.rs:503-506`) or port-node destruction.
- **Impact:** A captured pair under hard thrust/rigidization behaves as if the joint were infinitely strong — the "soft" applies to closing speed, not to sustained load. Player-visible effect: a docked vessel could be dragged along by the other with no structural consequence until the 192-tick window ends. Marginal severity because joints are transients and the capture window caps exposure at 3 s.
- **Suggestion:** Write each joint row's accumulated impulse into a `Contact`-shaped record (or a parallel `joint_impulses` out-parameter of `step`), attributed to the port nodes' hulls, so `external_loads` can include it — small change, same determinism. Alternative cheap mitigation: cap the joint's row impulse (a real force limit) or drop the joint on excess load — a soft capture that can be *torn off* is more honest than an unbreakable one.

### D3 — `Environment::for_body` silently produces a non-rotating contact surface for tidally-locked bodies *(latent defect; Low)*

- **Where:** `crates/csp-phys/src/simple.rs:434-441` (`for_body` — `spin_period_s: None → DVec3::ZERO`); data: `data/systems/home/rask/body.ron:16` (`rotation_period_s: None, // tidally locked`).
- **Problem:** `BodyDef::rotation_period_s: None` means *tidally locked* — rotation period equals the **orbital** period — but `for_body` maps `None` to `body_spin = ZERO`. On such a body the seeded heightfield (which is *body-fixed*) is evaluated as inertially static, while the body actually rotates in inertial space at orbital rate. Two consequences: (a) ground contact samples the wrong fixed phase of the heightfield — the terrain drifts under a landed vessel at `ω_orbit`; (b) the rotating-frame settle gates (`update_settle`, `:2333-2377`) and moving-surface contact velocity (`surface_vel_body`, `:592`) are disabled — a landed vessel can't benefit from co-rotating-frame rest and instead integrates against a static-frame surface.
- **Evidence:** The doc at `:428-433` acknowledges it: *"`None` means tidally locked, whose period is the orbital period — resolving that is the orbit layer's business, M2-C"* — i.e., callers must resolve it. The only production caller passes the field verbatim (`csp-view/src/lib.rs:1108-1111`, `terrin.rotation_period_s`). Currently unreachable: `physics.dominant` is fixed at world construction to Terrin (authored `21600.0`), and `to-bubble` refuses a vessel whose orbit parent isn't the dominant body (`csp-sim/src/lib.rs:5925`).
- **Impact:** If a bubble is ever instantiated around Rask (a tidally-locked moon with an authored colony), every surface interaction there runs the non-rotating branch on a rotating body. The effect magnitude is small (orbital-rate spin), but it's a silent physics divergence on authored data — exactly the class a PRD review exists to catch. Determinism is unaffected; correctness is.
- **Suggestion:** Change `for_body`'s contract: take the *resolved* period (or return an error/`Option`) so `None` cannot silently mean non-rotating — e.g. `for_body(body, center, resolved_spin_period_s)` where `None` input is a typed refusal when the body is tidally locked and the caller failed to resolve the orbital period. Or resolve `None` → orbital period inside the orbit layer before construction, with a `debug_assert` that tidally-locked bodies never reach `for_body` unresolved.

### D4 — `update_settle` counts vessel–vessel contact as latch-eligible *(edge case; Low)*

- **Where:** `crates/csp-phys/src/simple.rs:2331` — `let in_contact = !self.contacts[i].is_empty();` (pair contacts included; `self.contacts[i]` accumulates both ground and pair records).
- **Problem:** A body resting solely on *another vessel* can accumulate `settled_ticks` and latch — §2.6.4's settle latch is meant as surface rest. Once latched the body is a static collider (`inv_m = inv_i = 0`); if the supporting vessel later departs or unlatches, the latched body hangs frozen in inertial space — it skips `integrate_free`, generates no ground contacts, and only unlatches on throttle/`Unlatch`/activation.
- **Evidence:** Pair contacts write records on both bodies (`:1868-1869`, `:1938-1939`), and the latch at `:2399-2403` only checks `contacts[i].is_empty()` + velocity gates + pose deltas — nothing requires `peer.is_none()` (a ground contact). The gates do require near-rest *relative to the surface* for 128 ticks, so this needs two vessels in sustained mutual rest for 2 s — the common case (stacked vessels on the ground) is fine; the failure mode needs the support to unlatch/depart post-latch.
- **Impact:** A vessel can be left suspended mid-air after its support departs — a static collider hanging where the support was, until throttled or unlatched. Rare, deterministic, and recoverable; visually a floating vessel.
- **Suggestion:** Gate the latch on the presence of at least one *ground* contact (`contacts[i].iter().any(|c| c.peer.is_none())`) — matching the debris-impact rule at `csp-sim/src/lib.rs:4074-4079`, which already distinguishes `peer.is_none()`. If latching-on-vessel is intentional (it does enable stations resting on each other), document it in the module doc's §2.6.4 section — currently the gate's breadth is implicit.

### D5 — §2.9's 20 t-lander exit criterion is tested at the letter's intent, not its letter *(coverage gap; Low)*

- **Where:** `crates/csp-phys/src/simple.rs:2878-2932` (`box_dropped_on_sphere_converges_to_rest_and_latches`).
- **Problem:** PLAN §2.9 (PLAN.md:696-697): *"a 20 t lander rests on gear for 10 000 ticks with ‖v‖ < 1e-6, no visible jitter, and a state hash that becomes constant once latched."* The test is a 20,000 kg *box* (comment admits "the §2.9 20 t scale", `:2881`), latches within ≤4000 ticks, asserts jitter <2e-5 m/tick pre-latch and bitwise-constant state post-latch.
- **Evidence:** The jitter bound (`:2923-2926`) is stronger than "no visible jitter"; bitwise-constant post-latch (`:2929-2931`) is stronger than "hash becomes constant" — but the soak is 2.5× short of 10,000 ticks, the geometry is a box not a gear-legged lander (no gear parts exist anywhere in `data/parts/`), and `‖v‖ < 1e-6` is trivially satisfied post-latch since latch zeroes velocity.
- **Impact:** The criterion's spirit (a 20 t vessel rests stably, latches, stays bitwise-frozen) is met; the letter (10k-tick soak, gear legs) is not. Any long-tail instability past tick 4000 is unmeasured — e.g., secular drift on the curved sphere the test itself documents (`:2912-2917`).
- **Suggestion:** Extend the soak to 10,000 ticks (the test is already fast) and, when landing-gear parts exist, re-run with a multi-hull gear-legged craft. Cheap insurance for the spec's named gate.

### D6 — `SimpleBackend` has no mass gate: `mass_kg = 0` produces NaN state one tick before the sim's Fatal check *(robustness; Low)*

- **Where:** `crates/csp-phys/src/simple.rs:1592` (`b.vel = b.vel + force * (PHYSICS_DT / b.mass_kg)`), `:636`, `:702-704` (`1.0 / b.mass_kg`, `j_body / b.mass_kg`), `:1159` (`j / b.mass_kg`).
- **Problem:** Every force/impulse path divides by `mass_kg` unguarded. `weld()` requires total mass > 0 (`part.rs:222-227`), so a welded body can't hit this — but a hand-authored `WeldedBody` (tests, scenario/bench construction, MCP) with `mass_kg = 0` steps to `vel = NaN` inside the backend. The sim catches it *next* tick via `"non-finite body state mid-tick"` (`csp-sim/src/lib.rs:3806`) as `Fatal` — which aborts the whole tick range rather than refusing the offending spawn typed.
- **Impact:** A bad hand-authored body converts to a `Fatal` sim abort one tick late instead of a `Recoverable` at entry. `SimpleBackend` is the trust boundary that should say "I cannot integrate massless bodies."
- **Suggestion:** Validate `mass_kg > 0 && is_finite` at `step` entry (skip-with-error or refuse); alternatively assert at `WeldedBody` construction sites outside `weld()`.

### D7 — `Discrete` scale rule permits continuous `stretch` while `scale` is menu-locked *(design ambiguity; Low)*

- **Where:** `crates/csp-phys/src/resolve.rs:753-762` (`stretch_bounds(Discrete)` returns `[set.first(), set.last()]` — a *continuous* range), `:801-806` (`scale` must `set.contains(&scale)` — exact membership).
- **Problem:** On a `ScaleRule::Discrete` part, `scale` must be one of the authored sizes, but `stretch` may be *any* value in `[min, max]` — scaling the stack-axis geometry (`linear_z = s·t`) while every stat stays fixed (Discrete carries no exponents). A "Medium" part stretched to the max looks physically larger but has identical mass/capacity/thrust.
- **Evidence:** `:753-762` + the module-doc convention at `:72-81` documents Discrete = geometry-only scaling, and the validator's ban on `Tank`/`Engine` modules on Discrete parts (`:78-81`) removes the worst confusion — but structural/geometry-only parts still silently grow. Whether the VAB exposes stretch on Discrete parts is PRD-11 territory.
- **Impact:** Stats/geometry divergence authored through a legal resolved value. Probably intended (documented) but inconsistent — continuous stretch on a "menu of sizes" part defeats the point of discreteness.
- **Suggestion:** If Discrete is meant to pin dimensions, bound `stretch` to `{1.0}` (or to the same menu). If not, document why a size-menu part may be an arbitrary length.

## 3. Answers to the flagged review questions

**Q: Does the PGS backend correctly support the joint/island model (soft capture, merge, undock, stress across joints)?**
Mostly yes, with one gap. Soft-capture is a bilateral 3-row compliant joint inside the same PGS pass (`JointConstraint`, `simple.rs:984-1087`): exponential reel-in `−pull·C` clamped to `±max_correction` per axis, cold-started, fixed `(body_a, body_b, anchors)` sort, momentum-conserving (`apply_two_body_impulse`), latched sides static, self-joints and stale handles filtered (`:1097-1130`). The §2.9 hand-off at merge is implemented correctly (`joints.rs:959-979`): `v = p_total/m_total`, `ω` solves `I_merged·ω = L`. The 16-cap degrades to clean separation + `Recoverable` (`joints.rs:541-553`). Anchors re-derive per tick through `body_transforms` so re-welds can't stale them (`joints.rs:423-475`). **Gaps:** (a) no stress across joints (D2); (b) the §2.9 `RapierBackend`/hand-off event log doesn't exist — the documented deviation is coherent and the code is consistent with it, but §2.9's "transition tick is recorded in the event log" never happens because there is no transition to record (moot for saves — §7.4 refuses save with live joints, `joints.rs:37-50`); (c) `RapierBackend` is entirely absent — `rapier3d-f64`/`parry3d-f64` are workspace-pinned with zero dependents (`Cargo.toml:59-70`, single `impl PhysicsBackend` at `simple.rs:2412`) — the §2.9 oracle cross-check cannot run as specified.

**Q: The 20 t-lander criterion.** Substantially met, not literally — see D5. A 20 t body rests, latches, and freezes bitwise-constant; 4000-tick soak instead of 10,000, box geometry instead of gear legs (none exist).

**Q: Contact stability.** Good. Restitution-0 PGS at 8 iterations, Coulomb-disc projection (`:2019-2036` — better than the spec's per-direction clamps), position-level Baumgarte β=0.2 with a justified deviation from velocity-bias (`:166-174`), per-tick CoM/angular correction caps (`MAX_TICK_POS_CORRECTION`/`MAX_TICK_ANG_CORRECTION`), speculative anti-tunneling on both manifolds (`point_speculative` + `target_vn = depth/dt`), latched bodies as static colliders with `inv_m = inv_i = 0`, rotating-world surface-velocity targets. Known documented limitations: vertex-only generation (edge-edge crossing missed until a vertex crosses, `:126-133`), fixed-budget ordering bias in the position pass (ascending-order contacts consume the per-tick budget first — deterministic, resolves over a few ticks), and `mass_kg = 0` unguarded (D6).

**Q: Resolver single-source-of-truth — do editor/flight/contract consumers disagree on stats?**
No physics-stat disagreement is possible. `EffectivePart::weld_input` is the single projection to `WeldPart`; all consumers resolve through `resolve_part`/`resolve_parts`/`resolve_built_part`. The live inputs (`PartUsage`, `FamilyQualification`) only touch `EffectivePart.reliability` — `weld_input` (mass, CoM, inertia, collider, force sites, tanks, ports) is identical regardless. Consumers: editor Δv/TWR via `readout::analyze` → `resolve_parts` at `FRESH` quals (`readout.rs:157`); flight via `analysis.effective[*].weld_input` → `CraftDef.parts` (`csp-view/src/lib.rs:2082-2086`); inspector via `resolve_built_part` at FRESH (`vab.rs:1687-1694`); contracts read part *ids*, not resolved stats. The one intentional divergence: the editor displays unqualified hazard while the sim re-evaluates `qual_factor` on the live curve — documented (`readout.rs:154-157`, `vab.rs:2800-2814`, `ReliabilitySpec::from_effective` carries the curve). Manufacture-frozen upgrades compose identically on both paths (`compose_upgrade_levels` → `BuiltPart.upgrade_levels_at_build`).

**Q: `aero == None` — silently no-drag? should it refuse in atmosphere?**
Neither no-drag nor refusal — it's a *silent placeholder drag* (D1). In shipped flow unreachable (spawn installs, `ensure_aero` heals pre-integration each tick); for any consumer driving `PhysicsBackend::step` directly it's a silent wrong-physics channel. PLAN §2.4 wants refusal — the sim moved the refusal up to "self-install at spawn," which is a coherent deviation *for the shipped path*, but leaves the backend's `None` arm as an undocumented trap beneath it.

## 4. Verified-correct highlights (non-findings)

- **Integrator:** CoM-frame position advance (`:1608-1623` — `pos = x̄ − q·com_local`, not naive `pos += v·dt`); midpoint gyro term prevents explicit-Euler energy pumping (`:1595-1606`, test `:4154`); exact axis-angle position corrections (`apply_rotation_delta`, `:1136-1142`).
- **Solver ordering:** every loop in a fixed ascending order; joint list re-sorted so caller enumeration cannot affect the solve (`:1097-1130`, test `:4081`); cold-start per tick → no serialized solver state.
- **Two-body constraints:** equal-and-opposite write-back conserves momentum by construction; angular terms use world-frame `I_w⁻¹` via conjugate (`:840-849`); latched-side static handling consistent between contacts and joints.
- **Contact records:** `peer` distinguishes ground vs vessel contacts — the debris-impact rule (`lib.rs:4074-4079`) and save/warp predicates rely on it; hull attribution feeds `external_loads` → `joint_loads` correctly (`:1447-1462`).
- **`hull::point_penetration` boundary branch** (`hull.rs:246-283`) — correctly handles coplanar aligned boxes (the coincident-face case) with a half-thickness far-wall reject; this is the subtle piece that makes box-on-box vessel stacking work at all.
- **Terrain surface:** sim contacts the *same* displaced heightfield the renderer draws (`TerrainSurface`, `:281-353`), evaluated at `t+dt` post-integration spin phase; `cast_ray` fixed-count march+bisect is deterministic.
- **Resolver output gating:** every emitted family re-validated (`resolve_stats`, `resolve_envelopes`, `resolve_reliability` — an unvalidated def cannot leak NaN/∞); typed `ResolveError` → `SaveBlocking` everywhere including borderline caller-invariant cases, with the conservative mapping documented (`:160-170`); dual-Engine/dual-Lab refused (`:1818-1819`, `:1917-1918`); the `0/0` lerp in `qual_factor` is unreachable for valid curves (earlier window claims the shared abscissa — verified, the `qual_curve_valid` comment is correct).
- **Test coverage:** 38 tests in `simple.rs` — free fall, terminal velocity, rest/latch, jitter bound, bitwise determinism (single + two-vessel + joint), friction cone, moving-surface braking, spinning-world settle gates, anti-tunneling, momentum conservation, gyro energy, terrain-vs-datum contact; 31 in `resolve.rs` — full error-variant coverage, bit-identity + permutation safety, live-qualification re-eval, upgrade composition, every output gate.

## 5. Other observations (below defect threshold)

- `cast_ray` never intersects stepped bodies — documented (`:2497-2500`, "hull-vs-ray still waits on the parry `ConvexPolyhedron` materialization"). No current consumer needs it.
- `hulls_overlap`/`vessel_contact` re-derive `facet_planes` per call (O(n⁴)) and `vertex_margin` per vertex (`:1241-1253`) — `generate_pair_contacts` hoists per-body (`:1750-1764`), the on-demand predicate doesn't. Perf note only; the predicates run between steps, not in the hot loop.
- `wear_multiplier`/`apply_wear`/`hazard_per_s` are dead display stubs post-M9b (`resolve.rs:190-199`) — documented; cleanup tracked.
- `update_settle` `drot` uses `‖q₁−q_expected‖` — a quaternion sign flip would read ~2 and block latch forever, but producing one needs ~180°/tick of rotation — physically unreachable. Noted only because the measurement is `w`-sign-sensitive.
- `ensure_aero` on an airless world re-evaluates `aero_tables_stale` → early-`Ok` every tick per table-less `InBubble` vessel (`lib.rs:6219-6231`) — negligible wasted loop, no correctness effect.
