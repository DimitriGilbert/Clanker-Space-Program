# PRD-14 review — Map view

**Scope:** `crates/csp-view/src/map.rs` (2,472 lines) + cross-checks into `csp-view/src/lib.rs` (plumbing: `map_panels`, `map_pointer_input`, `set_mode`, `end_frame` staging, `recover_control`), `csp-ui/src/lib.rs` (`map_overlay`, `maneuver_panel`), `csp-sim/src/{lib.rs, maneuver.rs, transfer.rs, orbit.rs, events.rs}`, `csp-core/src/time.rs`, `csp-app/src/warp.rs`, `PLAN.md` §2.5/§2.8/§4/M5 row.

**Verdict:** WIRED and mechanically solid — camera/focus/zoom/pan, click-to-focus with id-anchored picks, orbit polylines with a quantized invalidation cache, apsides, single-node previews, site markers, starfield — with a genuinely good test suite (10 tests incl. the C12-F2 cache regression and the parabolic-sliver classifier). The focus-anchor lifecycle is done *right*: `focus_vessel` is an id anchor, `sync_map` re-anchors the index every frame and drops to the default body when the id leaves the snapshot (map.rs:480-498). But against the PRD the map is a **read-only orbit viewer**: the entire KAC-equivalent surface (§4 row "Alarms + transfer-window planner — v1 (M5)") is absent — no alarm set/list/fire surface, no transfer-window planner, no encounter/intercept prediction — even though `csp-sim` ships all three (`SetAlarm`, `WatchTransferWindow`, `plan_transfer`, `predict_encounter`). The §2.5 `presentation_tick` rule is not implemented anywhere. And the map under-reports the program it should mirror: landed vessels vanish, colonies never appear, the active vessel is indistinguishable.

---

## Findings

### F1 — §4 KAC-equivalent is absent: no alarm surface, no transfer-window planner — HIGH

- **Where:** whole file — nothing in `map.rs` references alarms or transfer windows; `csp-view/src/lib.rs:638-690` (`map_panels`) draws only `map_overlay` + `maneuver_panel`. Grep confirms zero `SetAlarm`/`WatchTransferWindow`/`plan_transfer`/`porkchop`/`predict_encounter` references in `csp-view`, `csp-ui`, `csp-app`.
- **Problem:** PLAN §4 commits "Kerbal Alarm Clock — alarms + transfer-window planner (falls out of the event queue) — **v1 (M5)**", and the M5 exit row (PLAN.md:1501) lists "Lambert/porkchop planner; encounter prediction; transfer-window events". The sim delivers all of it — `SimCommand::SetAlarm` (csp-sim lib.rs:554), `WatchTransferWindow` (lib.rs:730), `EventKind::PlayerAlarm`/`TransferWindow` (events.rs:164,194), `plan_transfer`/`porkchop_scan` (transfer.rs:1007+) — but the player cannot set an alarm, list pending alarms, see a fired one, or plan a transfer window. Worse, a fired `PlayerAlarm`/`TransferWindow` event produces **no player-visible output at all**: the only notice feed (`csp-view/src/lib.rs:2987-3002`) maps exclusively reliability `PartFailed`/`IgnitionMisfire` notifications into program-window rows — an agent-set alarm firing is a silent no-op.
- **Evidence:** `maneuver_panel` (csp-ui/lib.rs:1027-1089) is the only map-adjacent planning surface: vessel picker + `T+` seconds + three dv DragValues. No alarm tab, no window list, no countdown to a transfer opportunity.
- **Impact:** a listed v1 feature row is functionally `[MISSING]` at the player layer; the M5 "interplanetary" promise is reachable only via hand-tuned nodes, while ~1.5k lines of porkchop/window machinery are agent/test-only (`sim.command` MCP tool, scripts, bench).
- **Suggestion:** (a) an Alarms section in the map overlay (or program window): emit `SimCommand::SetAlarm`, mirror pending `PlayerAlarm`/`TransferWindow` heap entries into `MapUiData`, and surface fired events through the notice channel (`flight_notice`/`notice_overlay` is already the global cue stack); (b) a "plan transfer" affordance that calls `plan_transfer`/`porkchop_scan` and offers `SetManeuver` + `WatchTransferWindow` — the destination picker can reuse the existing `MapPick`/`BodyTable` machinery.

### F2 — §2.5 `presentation_tick` rule not implemented: map evaluates at `snap.tick` — MEDIUM

- **Where:** `map.rs:729` (`let t = snap.tick;` — every body/vessel position and label ETA), staged at `map.rs:1383` (`tick: sim.clock()`) / `csp-view/src/lib.rs:1528`.
- **Problem:** §2.5 (PLAN.md:396-404) requires the map to evaluate `OrbitModel::state_at(presentation_tick)` where `presentation_tick` is "a separate, non-authoritative f64 value that may lie between the pre- and post-advance clock", explicitly because "snapping an orbit map by 18 sim-minutes per frame is not acceptable". Nothing implements it: `SimTime` is a `u64` tick (csp-core/time.rs:21), `state_at` takes `SimTime`, and no fractional/presentation clock exists in `csp-view`. Under rails warp the ladder reaches ×10⁵ (csp-app/warp.rs:10, `WARP_LADDER`) — ~18–28 sim-minutes per 60 fps frame — and every marker/polyline offset teleports by exactly that increment.
- **Impact:** at ×1–×100 the snap is sub-perceptual; at ×10³+ (the regime §2.5 wrote the rule for — "warp is the exact situation in which the player is looking at the map") vessel markers jump a visible arc fraction per frame and body positions strobe. Spec-rule violation with a real visual artifact, not a determinism risk (presentation-only).
- **Suggestion:** stage a `presentation_tick` (f64 seconds or fractional ticks) in `MapSyncInput` — e.g. `last_tick + elapsed_wall × warp_level` — and add a float-time evaluation path (`state_at` already resolves arbitrary `SimTime`; either accept fractional ticks or evaluate at `floor/ceil` and lerp positions). Cheapest honest version: keep `t = snap.tick` but lerp body/vessel positions between the previous and current snapshot tick by the frame's fractional remainder.

### F3 — No encounter/intercept prediction display (M5 "encounter prediction") — MEDIUM-HIGH

- **Where:** `map.rs:1070-1098` (`refresh_node_previews`) draws `csp_sim::maneuver::predict_maneuver` — a single post-burn conic **in the same parent frame** — and nothing else; `predict_encounter`/`EncounterPrediction`/`EncounterApproach` (transfer.rs:1306-1409: crossing tick, approach periapsis, `v_inf`, `impacts`, rebased conic for chaining) are never called from the view layer.
- **Problem:** the map shows "node → predicted conic" but never answers the maneuver-preview question that matters: *does this burn encounter anything?* No SOI-crossing markers on the flown or predicted line, no "Rask encounter T+X d · Pe 120 km" label, no post-transition conic chain, no `impacts: true` warning when the predicted periapsis is under the surface. No vessel↔vessel intercept/closest-approach either (rendezvous aid; the multi-vessel mechanics exist but there is no targeting concept at all — `focus` is camera-only, `recover_control` reads it at lib.rs:1919 but nothing computes relative trajectory).
- **Evidence:** `refresh_node_previews` samples `predicted` then stops; `sample_orbit` draws the conic regardless of SOI boundaries; `soi_m` (map.rs:185) is used only for focus framing (`default_distance`, map.rs:410), never rendered.
- **Impact:** the M5 node preview is a prettier guess — a player planning the Duva transfer cannot see whether the predicted conic enters Duva's SOI or what the approach looks like, which is precisely what `predict_encounter` computes. It also quietly *lies by omission*: the green line keeps drawing past the point where the sim will re-parent the conic.
- **Suggestion:** after `predict_maneuver`, run `predict_encounter(model, predicted, now, horizon)` — and the same on the flown orbit — and render the `Enter`/`Exit` event as a labeled marker ("SOI exit → solen T+…", "Duva encounter Pe … km, v∞ …") plus optionally the `rebased` conic as a second dashed polyline; `approach.impacts` deserves a warning tint.

### F4 — Map under-reports the player's program: landed vessels vanish, colonies never drawn, no active-vessel distinction — MEDIUM

- **Where:** `capture_sync_input` `filter_map` (map.rs:1385-1405) — a `SurfaceLatched` vessel has neither `orbit()` nor `body()` (csp-sim lib.rs:377-391) so it is skipped outright ("a parked craft has no conic to draw", map.rs:1376-1380); site markers are `SiteTable` launch/recovery sites only (structures.rs:78-95) and only on the dominant body (`map.rs:894-912` — "a site on any other body has no staged rotation to place it by, so it is skipped honestly"); all vessels share `VESSEL_COLOR` + `vessel {id}` labels (map.rs:811).
- **Problem:** (a) a landed/returned vessel disappears from the map entirely — the `focus_vessel` anchor correctly drops to the default body (sync_map:491-495), but the vessel itself is gone from the only program-level view; its surface pose (`SurfacePose` + `latched_pos`, transfers.rs:708) is never projected. (b) Colonies — including the authored Rask colony (`data/systems/home/colonies.ron`, founded at boot per csp-view/lib.rs:1218) — are not `SiteEntry`s and have no marker or label; a colony body in the snapshot (`colonies` arena) is invisible. (c) The vessel being flown (InBubble, lease `Player`) is indistinguishable from debris — same orange disc, same label shape; after a breakup the map fills with identically-labeled "vessel N" debris.
- **Evidence:** `Vessel` has no `name` field, so `vessel {id}` labels are honest — the gap is markers/state, not naming.
- **Impact:** the map — the natural home for "what does my program look like" — shows fewer objects than the sim owns; the user-facing symptom is "my landed craft / colony is gone" even though the sim state is intact. Compounds PRD-07's hidden-colonies problem: the one authored colony is doubly invisible (no panel, no marker).
- **Suggestion:** (a) draw latched vessels as surface markers reusing `site_world_pos`-style pose math (spin phase is already staged for the dominant body; for other bodies a fixed-frame pose is still honest as a marker); (b) add colony sites to `SiteTable` or a parallel `ColonyTable` staged from `sim.colonies()`; (c) carry `is_active`/`is_debris` into `MapSyncInput` (debris_since exists on the vessel) and vary marker style — active vessel brighter/ringed, debris dimmed or a distinct glyph.

### F5 — Maneuver support is dominant-body-only and form-only — MEDIUM

- **Where:** `apply_set_maneuver` rejects non-OnRails vessels and `orbit.parent != dominant` (csp-sim lib.rs:6018-6025); the panel exposes `T+` seconds + dv fields (csp-ui/lib.rs:1059-1087); preview is one impulsive conic (map.rs:1076).
- **Problem:** three coupled thinnesses. (a) *Residency*: `SetManeuver` only applies to on-rails vessels — the panel correctly filters (P09-F2, lib.rs:665-669) but there is no affordance to get the flown vessel eligible (no `ToRails` surface), so for a vessel currently InBubble near the pad the picker silently shows nothing or another vessel. (b) *Frame*: `orbit.parent != dominant` refuses nodes around Rask/Duva/Solen — a transfer can only get a departure node at Terrin; no mid-course-correction node in heliocentric space, no insertion node at the destination. The executor needs the dominant env to materialize the burn — a documented sim constraint, but the map presents it as "maneuvers" without telling the player only Terrin-frame nodes are possible. (c) *Ergonomics*: placement is "T+ seconds", not click-on-orbit or anomaly ("next periapsis"), and there is no Δv/burn-time readout against the vessel's capability.
- **Impact:** for the M5 home+moons slice the single Terrin departure node suffices — but the player gets no warning that a second node, a correction, or an insertion can't be expressed; the green preview implies more than the sim will do.
- **Suggestion:** honest surfacing beats features here: (a) the picker row should say why a vessel is ineligible (InBubble → "in physics bubble — go to rails first", non-dominant parent → "nodes only around {dom}"); (b) the node label could add the burn-time estimate the HUD already computes (`burn_full_s` staged in `FlightUiData`).

### F6 — Map opens focused on the star, not the flown vessel — LOW-MEDIUM

- **Where:** `MapInput::new` → `focus: table.default_focus` (map.rs:275) — the root body; `ToggleMode`/`set_mode` only `refocus()` the retained focus (map.rs:294-296, lib.rs:1822-1845). Nothing links `FlightFocusOverride` or the player-lease vessel into map focus.
- **Problem:** the first `M` press during flight shows the whole system at 6e10 m — the player's LEO vessel is an invisible dot inside Terrin's marker — and `Tab` cycles alphabetical `BTreeMap` body order (test at map.rs:2058-2066 shows `m, p, sol`; shipped order is duva/rask/solen/terrin), not hierarchy order. KSP's map opens on the active vessel.
- **Evidence:** `focus_vessel` writes exist only in `apply`/`sync_map`; `recover_control` reads the focus as a recovery target (lib.rs:1919) — the focus concept already doubles as vessel targeting, but nothing seeds it.
- **Impact:** first-impression papercut on every session — the player must hunt for their own craft; cheap to fix since `flight_snap`/the pin already know the controlled vessel id.
- **Suggestion:** on `ToggleMode`/`set_mode` into Map with `focus_vessel == None`, seed `focus_vessel` from the `FlightFocusOverride` target or the vessel holding the `Player` lease before `refocus`.

### F7 — `sample_orbit` samples uniform in mean anomaly: periapsis is starved on high-e conics — MEDIUM

- **Where:** `map.rs:1464-1467` — closed-orbit branch samples `t = epoch + period·i/128`, i.e. uniform in M.
- **Problem:** uniform-M places samples where the vessel lingers (apoapsis). Near periapsis, dM/dν = (1−e²)^{3/2}/(1+e·cos ν)² — at e = 0.9 that is ~0.023, so consecutive samples bracket ν = 0 up to ~±2 rad away and the polyline *chords* the periapsis at ~3× its true radius; at e → 0.99 the near-periapsis arc can get zero samples inside ±π/2 and the drawn "orbit" cuts straight through the interior. The open branch already does the right thing (uniform in ν, map.rs:1486-1488) — the closed branch is the inconsistent one.
- **Impact:** the silhouette can mislead exactly on the trajectories M5 is about (high-e transfer/escape legs, atmosphere-grazing arcs): the drawn orbit appears to clear the body/atmosphere when the true conic dips in. The numeric `MapOrbitInfo` Ap/Pe stay honest — it's the drawn line that's wrong.
- **Suggestion:** sample uniform in eccentric anomaly (`E` uniform, `M = E − e·sin E` into `state_at`) or uniform in ν like the open branch — the silhouette then always resolves the apsides within 1/128 of the conic.

### F8 — Burning-node preview keeps showing the original impulsive plan with "T−0 s" — LOW

- **Where:** `map.rs:838` (`eta` saturates at 0 once `node.tick` passes) + `refresh_node_previews` keyed on `(orbit_key, node)` — `predict_maneuver` always applies the *full* commanded Δv impulsively at the node point.
- **Problem:** during a burn the vessel is InBubble (refit every frame → re-key every frame → `predict_maneuver` re-solves each frame anyway, so no stale-cache hazard), but the green line keeps showing the original full-Δv plan while the label reads `T−0 s` — never "burning, Δv remaining …". `ManeuverStatus::Burning(ActiveBurn).dv_remaining_mps` is staged but unused.
- **Impact:** cosmetic — during long burns the preview diverges from the remaining intent and the countdown freezes; bounded because the burn completes and the node clears.
- **Suggestion:** gate the label on `node.status`: `Burning` → "burning · Δv left {dv_remaining}"; optionally re-predict remaining-Δv from the current state instead of the node point.

### F9 — Pre-latch / grounded InBubble vessels draw a degenerate osculating ellipse — LOW

- **Where:** `map.rs:1391-1404` — the InBubble branch fits `cartesian_to_elements` on `com_world`/`vel` with no degeneracy gate (compare `burn_frame`'s `BURN_FRAME_H_TOL`, maneuver.rs:153-175).
- **Problem:** a vessel resting on the pad during the 128-tick settle window before `SurfaceLatched`, or a landed-not-latched craft, has near-`ω×r` velocity → the fitted conic is a sub-surface-skimming ellipse that draws a spurious orbit line through the planet (or `Err` → skipped — data-dependent). Sub-orbital/impacting trajectories also draw the *full* ellipse including the underground arc — no impact-point clip or marker (`predict_encounter`'s `approach.impacts` would flag it, see F3).
- **Impact:** a wrong-looking line for up to ~2 s per landing/settle; honest noise for genuinely ballistic arcs (the underground half of the ellipse is drawn like KSP does pre-impact, but never annotated).
- **Suggestion:** skip fitting when the state is in settled contact / below the surface (`rel.norm() <= env.radius_m`), or clip the polyline at `r < parent radius` and drop an impact marker.

### F10 — Minor polish notes — LOW

- **Focus-cycle order** is `BTreeMap` alphabetical (map.rs:304 + test:2058-2066) — the star lands mid-cycle and moons precede their parents; cycling by hierarchy depth would read better.
- **Node preview re-key during `Burning`:** `node.clone()` in the cache key (map.rs:1073) includes `ActiveBurn.dv_remaining_mps`, which decrements every tick — the preview re-derives every frame while burning. Harmless (the InBubble orbit key churns anyway; ~130 solves/frame for one vessel) but the key could compare `Scheduled`-stable fields only.
- **No apsides on the predicted conic:** `focus_apsis` marks only the flown orbit (map.rs:851-886); KSP marks the predicted orbit's Ap/Pe too — the numbers live in `predicted.elements`, cheap to add.
- **μ-source split:** the InBubble conic is fitted under `env.mu_m3_per_s2` (map.rs:1394) but re-evaluated under the model's `body_orbit(parent).mu` (map.rs:742, 1450). They agree today (both from the same body defs); a data set where physics-env μ ≠ orbit-model μ would silently drift the marker — worth a constructor-time consistency assert rather than a per-frame concern.
