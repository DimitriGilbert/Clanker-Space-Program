# Review — Cluster C22: `apps/telemetry` (TanStack dashboard SPA)

Scope: every file listed in the cluster plus the csp-server wire/schema mirrors
(`crates/csp-server/src/{http,dashboard,telemetry}.rs`, `crates/csp-sim` field
names, `crates/csp-server/tests/e2e.rs`). I ran `npx vite build` +
`scripts/finalize.mjs` to verify the build contract end-to-end.

## Verified-correct items (checked, no finding)

- **Wire envelope**: client `{proto:1, kind:"subscribe", fields, rate_hz}` and
  inbound `telemetry`/`subscribed`/`error`/`command_ack` handling match
  `http.rs::ws_session` exactly (`seq`, `tick`, `payload`, `unknown_fields`).
- **`?token=` auth**: `ws.ts:46` matches `http.rs:223-227` (`TokenQuery` on the
  same URI as `McpQuery.client`); `?client=telemetry-spa` matches
  `ws_upgrade`'s `Query<McpQuery>`.
- **Meta-tag token**: server injects `<meta name="csp-token" …>` before
  `</head>` (`http.rs:261-266`); the built `_shell.html` has a real `</head>`
  and `cspToken()` reads the same name.
- **Dashboard doc schema**: `Dashboard`/`Widget`/`Rect` field-for-field match
  the Rust `#[serde(deny_unknown_fields)]` structs; `WIDGET_KINDS` mirrors
  `registry.tsx`; `rate_hz` divisor set identical; `subscriptionFields()` is
  the same dedupe+sort as `dashboard.rs::subscription_fields`.
- **Field paths**: every path in `dashboards/default.json` resolves against
  `VesselTelemetry`/`TelemetrySnapshot` (`vessels.0` works because `BTreeMap<u64,…>`

  `elements`/`pos_m` are `{x,y,z}`-shaped: `csp_core::DVec3` derives `Serialize`

  type-correct.
- **`routeTree.gen.ts`**: exists, is consistent with the two routes, and is
  regenerated by the plugin on build — the explorer's concern is unfounded.
- **Build contract**: `vite build` emits `dist/client/_shell.html` +
  `dist/client/assets/*` with `/assets/...` URLs (matching `/assets/{*path}`);
  `finalize.mjs` promotes `_shell.html` → `index.html` successfully.

## Findings

### [MEDIUM] Finding 1: orbit-map projects `pos.z` — the out-of-plane axis — for the in-plane vessel marker
File: `apps/telemetry/src/lib/widgets/orbit-map.tsx:42-47`

**Problem**: The marker projects `pos_m` as (x → right, **z → down**), but the
sim's orbital plane for any equatorial orbit is the **x–y plane** — `z` is the
orbit normal. `cartesian_to_elements` measures inclination from +z
(`orbit.rs:742`, `atan2(√(hx²+hy²), hz)`) and `perifocal_to_inertial`
(`orbit.rs:598-607`) puts planar motion in x/y, so `pos.z ≡ 0` for every
equatorial orbit — the overwhelmingly common case. The marker's screen-y is
therefore frozen at `80` and it slides along a horizontal diameter regardless
of true anomaly.

Worse, it can never coincide with the drawn conic: at periapsis the true
position is `r_p·(cos ω, sin ω, 0)`, and the ellipse's periapsis vertex is
drawn at screen `(100 + r_p·cos ω·s, 80 − r_p·sin ω·s)` (the `rotate(−ω)` +
`cy = 80 + c·sin·s` convention is internally consistent, equivalent to mapping
in-plane y → screen-up). The marker reads neither `y` nor a consistent sign, so
even for inclined orbits it displays the out-of-plane component on the axis the
ellipse uses for the in-plane coordinate.

**Evidence**: `orbit-map.tsx:44-46` `pz = num(pos.z)` / `vy = 80 + pz*scale`;
comment at `:39` claims "in-plane projection (x→right, z→down)".
`csp-sim/src/orbit.rs:563` `periapsis_state` returns `DVec3(r_p, 0, 0)` in
perifocal x–y; `:598-607` rotates into inertial x–y when `i = 0`.

**Impact**: The green vessel dot is wrong in every non-degenerate case —
pinned to the horizontal centre-line for equatorial orbits and visibly off the
drawn ellipse whenever `ω ≠ 0`. The widget is labeled "schematic" but the
marker actively misleads (x-coordinate is right, y is from the wrong axis).

**Suggestion**: project `pos.x`/`pos.y` (the actual in-plane components) and
use `vy = 80 − pos.y·scale` to match the ellipse's `rotate(−ω)` convention —
or rotate the ellipse with `+ω`/`cy = 80 − c·sin·s` and keep `+y` down-screen;
either way marker and ellipse must share one axis convention.

### [MEDIUM] Finding 2: no reconnect/resubscribe path — a dropped socket leaves a dead dashboard showing stale data
File: `apps/telemetry/src/lib/ws.ts:81-83`,
`apps/telemetry/src/routes/index.tsx:16-36, 45`

**Problem**: `subscribeTelemetry` opens the socket once and returns only a
close handle ("reconnects are the caller's decision"), but the only caller
subscribes exactly once in a `[]`-deps effect. On `onclose`/`onerror` the page
sets `conn` to `'closed'`/`'error'` and stays there forever, while
`frame.current` retains the last telemetry — the header keeps printing
`· tick N` and every widget keeps rendering hours-old values. There is no
retry, no frame-staleness check, and the error `detail` string (e.g.
`"rate_hz must divide 64"`) is dropped (`onState: (s) => setConn(s)`).

**Evidence**: `index.tsx:16-36` — single `loadDashboard().then(subscribe)`;
cleanup only closes. `ws.ts:82` `ws.onclose = () => opts.onState?.('closed')`.

**Impact**: any transient disconnect (server restart, socket error) silently
degrades the dashboard to a stale-data museum; the only recovery is a manual
reload. (Note: after a *server* restart the injected token rotates, so reload
is genuinely required — but a transient drop on a still-live server could be
recovered in place, and at minimum the stale frame should be cleared/marked.)

**Suggestion**: add a bounded retry loop in `DashboardPage` (re-run
`subscribeTelemetry` on `'closed'` with backoff), clear `frame.current` on
disconnect, and surface `detail` on the `'error'` state.

### [LOW] Finding 3: `.dash-grid` has no row sizing — `rect.h`'s "tile-height unit" does not exist
File: `apps/telemetry/src/styles.css:66-70`,
`apps/telemetry/src/routes/index.tsx:55-56`

**Problem**: The grid declares only `grid-template-columns: repeat(12, 1fr)`
and `gap` — no `grid-auto-rows` (or `grid-template-rows`). `w.rect.h` spans
therefore reference auto rows sized by content, while the server schema
documents `rect` as "row units of the SPA's tile height"
(`dashboard.rs:90-101`). An `h: 2` vs `h: 4` widget gets whatever height its
content implies, and `.widget-tile`'s `min-height: 0`/`flex-1` chrome is built
for fixed-height tiles that never materialize.

**Evidence**: `styles.css:66-70` `.dash-grid { display:grid; grid-template-
columns: repeat(12,1fr); gap:12px; }` — no row rule anywhere in the file.

**Impact**: layout still roughly works (grid distributes spanning items across
auto rows), but `h` is not the contracted tile-height unit; tiles collapse to
content height and heights vary with data, so the stored layout does not
render the grid it describes.

**Suggestion**: add e.g. `grid-auto-rows: 72px;` (whatever the intended tile
unit is) to `.dash-grid`.

### [LOW] Finding 4: no inbound `proto` check — a future proto-2 stream is silently consumed
File: `apps/telemetry/src/lib/ws.ts:68-79`

**Problem**: The envelope's `proto` is "bumped on any breaking change"
(PLAN §2.12.2), and the client asserts `proto: 1` on the *outbound* subscribe
(the server enforces it). But inbound frames are dispatched on `kind` alone —
`msg.proto` is never read. A `proto: 2` server speaking a changed `payload`
shape would be accepted and silently misrendered.

**Evidence**: `ws.ts:68` `if (msg?.kind === 'telemetry') { … }` — no
`msg.proto` check; `TelemetryFrame` doesn't even carry `proto`.

**Impact**: silent wrong-data display on a wire-version bump — exactly the
failure mode `proto` exists to prevent. Low severity only because proto is 1
today on both ends.

**Suggestion**: check `msg.proto === WIRE_PROTO` in `onmessage` and surface an
error state on mismatch.

### [LOW] Finding 5: `unknown_fields` is collected but only the gauge surfaces it
File: `apps/telemetry/src/lib/ws.ts:16, 73`,
`apps/telemetry/src/lib/widgets/{graph.tsx:19, table.tsx:22, orbit-map.tsx:18}`

**Problem**: The server deliberately reports unresolved paths in
`unknown_fields` (`telemetry.rs:94-110` — "never silently dropped"). Only
`GaugeWidget` checks it (`gauge.tsx:19` → "unknown field …"). For table rows,
graph, and orbit-map, an unknown/typo'd path is visually identical to a
legitimately-absent value: `—`, a frozen sparkline, or "no conic — vessel not
on rails" (which mislabels an authoring error as a sim state).

**Impact**: dashboard authoring errors (the entire point of the server-side
`unknown_fields` mechanism) are invisible on 3 of 4 widget kinds.

**Suggestion**: a shared `unknown` badge/row style; e.g. table rows render
`unknown field` for `f ∈ frame.unknown_fields`, orbit-map distinguishes
"field not on wire" from "no conic".

### [LOW] Finding 6: graph window sizing hardcodes 16 Hz regardless of the dashboard's `rate_hz`
File: `apps/telemetry/src/lib/widgets/graph.tsx:13-15`

**Problem**: `cap = window_s × 16` assumes 16 samples/s, but `rate_hz` is a
per-dashboard knob (any 64-divisor is valid and the server honors it). At
`rate_hz: 8` a `window_s: 60` graph actually spans 120 s; at 64 it spans 15 s.
The widget receives no rate — `WidgetProps` is `{def, frame}` — so it can't
size the window correctly even if it wanted to.

**Evidence**: `graph.tsx:14` `const rate = 16 // samples/s assumed for window
sizing`; `index.tsx` passes only `def` + `frame`.

**Impact**: incorrect time windows on any non-16 Hz dashboard — silent, and
the shipped default (16 Hz) masks it.

**Suggestion**: thread the effective rate through (`WidgetProps.rate_hz` or a
`subscribed` ack's `rate_hz`, which the server already sends and the client
already receives but ignores at `ws.ts:75-76`).

### [LOW] Finding 7: `vite dev` has no path to csp-server — `/ws` and `/api/*` hit the dev server
File: `apps/telemetry/vite.config.ts` (whole file),
`apps/telemetry/src/lib/ws.ts:44`

**Problem**: `new URL('/ws', window.location.href)` makes the WS target
same-origin. Under `vite dev` (port 47901) that is the Vite server itself:
there is no `server.proxy` config, so `/api/dashboards` 404s (masked by the
bundled-default fallback — see Finding 8) and the `/ws` upgrade is never
answered by anything (Vite's HMR socket only claims `vite-hmr`/`vite-ping`
protocol upgrades), leaving the page stuck at `connecting`.

**Impact**: dev-mode renders a plausible-looking dashboard that can never go
live, with no hint that a proxy or the csp-server-served build is required.

**Suggestion**: add a `server.proxy` for `/ws` (ws: true) and `/api` to a
configurable csp-server origin, or document/serve exclusively through
`spa_dir`.

### [LOW] Finding 8: `loadDashboard` swallows all failure modes; `saveDashboard` error is a bare bool and neither is surfaced
File: `apps/telemetry/src/lib/dashboard.ts:56-81`,
`apps/telemetry/src/routes/index.tsx:19-31`

**Problem**: `loadDashboard` falls back to the bundled default on *any*
non-`res.ok`/throw — a 503 "dashboards not configured", a 400 from a stored
document that fails `deny_unknown_fields`, and "nothing stored yet" are
indistinguishable, and nothing (not even a console log) records which happened.
`saveDashboard` returns a bare `bool` and has no caller — the SPA has no
dashboard-persistence UI despite the server exposing PUT + the `dashboard.*`
MCP tools, so the whole write path is dead code that silently discards server
validation messages (which are detailed: `"invalid dashboard: …"`).

**Impact**: a broken store or a rejected document looks exactly like "fresh
install"; PUT failures would be invisible to a future editor UI unless it
re-fetches.

**Suggestion**: return a tagged result (`{kind: 'stored'|'default'|'error',
detail?}`) and log/display the fallback reason; have `saveDashboard` surface
the server's 400 message.

## Non-findings (deliberately checked, ruled out)

- **`unsubscribe` kind**: mentioned in the cluster context, but neither side
  implements it and the spec doesn't require it — teardown is `ws.close()`.
  Not a mismatch.
- **`pos_m`/`DVec3` wire shape**: `csp_core::DVec3` derives `Serialize` as a
  struct → `{x,y,z}` object; the orbit-map's property access is type-correct
  (the axis *choice* is the bug, Finding 1 — not a shape mismatch).
- **MessagePack arrays**: deferred by declaration in `http.rs:27-35`; JSON-only
  is the documented current contract.
- **`spa_dir` unwired in shipped binaries**: known and documented deferral at
  `http.rs:47-51`; not an SPA-side bug.
- **StrictMode dev double-push** in `GraphWidget`'s effect: dev-only cosmetic.
