### Finding 2: No-GPU hosts make the gate silently pass; CI has no lavapipe and no skip detection — CONFIRMED
**Original**: `headless_device() -> None` makes both gate tests eprintln+return (a pass); CI losing lavapipe turns the gate into a permanent green no-op.
**Verification**: Skip logic exact at render_gate.rs:262-265 and 336-339 (`let Some((device, queue)) = headless_device() else { eprintln!("render-gate: no headless GPU adapter (install lavapipe) — skipping"); return; };`). grep of the file shows no `CI` env check and no required-mode var — the only env::var reads are DUMP_* knobs in #[ignore]d dumps. Stronger than reported: .github/workflows/ci.yml (lines 11-28) runs plain `cargo test --workspace` on `ubuntu-latest` with **no Vulkan/lavapipe installation step**, while the gate's own doc (render_gate.rs:12-14) claims lavapipe "provides a real Vulkan adapter on dev/CI boxes" — an assumption the workflow never establishes. GitHub-hosted ubuntu runners ship no Vulkan ICD, so the gate most likely has *never executed* in CI, not merely "would stop if lavapipe were lost". Nuance: skip-on-no-adapter is a conventional pattern for gfx tests and the skip is documented (render_gate.rs:31-34); the defect is the absence of any required-mode/skip-count signal, which is what makes it MEDIUM rather than style.

### Finding 3: Focus-pin release branches on `reason().starts_with("to-bubble")` — CONFIRMED
**Original**: Branching on SimError diagnostic text across a crate boundary violates the type's documented "never branch-determining" contract; a message reword silently resurrects the P04-F2 pin-hijack bug.
**Verification**: Code exact at crates/csp-view/src/lib.rs:1182-1186. Contract exact at crates/csp-core/src/error.rs:12-14: "Payloads are `&'static str` diagnostic text intended for logs, dialogs, and bug-report bundles only — they are never hashed, never serialized into the canonical stream, and never branch-determining." Six "to-bubble: ..." literals live only in csp-sim (crates/csp-sim/src/lib.rs:5601,5605,5608,5611-5613,5616,5633); grep finds no shared const / RejectKind anywhere, and no test pins the prefix or exercises the drain-reject release (greps for `starts_with("to-bubble")`, `RECOVER FAILED`, `ToBubble` across tests: empty). The `RejectedCommand` record (csp-sim/src/lib.rs:1198-1215) carries only `key: CommandKey` + `error: SimError` — no typed kind exists to match on, confirming the fix requires new surface. Additional defect found during verification, strengthening the finding: csp-sim/src/lib.rs:5621 maps a weld failure inside `apply_to_bubble` to `Recoverable(e.reason())` (weld's own text, no "to-bubble" prefix), and `state_at`/`ensure_aero` errors likewise lack the prefix — so even *today*, with no rewording, a ToBubble rejection that fails at the weld/state/aero step does not release the pin. The prefix match is incomplete against the current producer, not merely fragile against future edits.

### Finding 4: Second launch overwrites the single StagePlan resource — CONFIRMED
**Original**: `launch_craft`'s unconditional `insert_resource(plan)` discards the incumbent plan; the first craft's unfired stages become permanently unfireable and the HUD describes the new craft.
**Verification**: crates/csp-view/src/lib.rs:1868 (`StagePlan::for_launch`) and 1886 (`self.world.insert_resource(plan);`) — no read of the incumbent, no notice. `StagePlan` derives `Resource` (crates/csp-view/src/flight.rs:609-610) — a per-type singleton; the only production insert sites are the default at lib.rs:1054 and this overwrite, and `set_mode` (lib.rs:1502-1530) never touches it. The same type's doc (flight.rs:600-608) states the opposite design: "The plan belongs to the vessel its launch spawned — NOT the flight focus: a newer spawn ... can take the focus ... without ever retargeting this plan" — the fingerprint/`min_id`/`ambiguous` machinery (flight.rs:617-639, 687-712) exists precisely to keep a plan firing at its own vessel, which the wholesale replacement defeats. Scenario reachable: tests/stage_plan.rs:159-190 launches a second craft while the first vessel is provably still live in the arena (asserts on both `vessels()[&first]` and `vessels()[&focus]`). "Papers over" claim exact: stage_plan.rs:164-166 manually re-`insert_resource`s a `StagePlan::bound_to(..., first)` after the second launch — the production path never restores it (in that test the incumbent plan happened to be empty because the starter craft is single-stage, so the overwrite destroys nothing there — the gap is never exercised). HUD reads the same single resource (lib.rs:418-419; flight.rs:478-484).
