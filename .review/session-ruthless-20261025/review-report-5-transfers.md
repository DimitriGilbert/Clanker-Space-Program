### [SEVERITY: HIGH] Finding 1: Burning maneuver node is silently destroyed on unlatch, though two doc contracts (and the restore gate) promise it resumes
**File**: crates/csp-sim/src/maneuver.rs:[59-62] and crates/csp-sim/src/maneuver.rs:[113-118] (behavior at crates/csp-sim/src/lib.rs:3369)
**Problem**: maneuver.rs documents, twice, that a mid-burn surface latch holds the countdown and unlatch resumes it. Module doc: "A `Burning` node survives the §2.6.4 latch/unlatch round-trip (a latched vessel cannot burn; unlatching resumes the countdown where it stopped)." Variant doc on `ManeuverStatus::Burning`: "the vessel is bubble-resident (or §2.6.4-latched mid-burn — the countdown holds while latched and resumes on unlatch)".
**Evidence**: The runtime supports the documented state: latch capture (lib.rs:9798-9801, `vessel.state = VesselState::SurfaceLatched(pose)`) leaves `v.maneuver` untouched, and `World::restore` explicitly accepts it (lib.rs:9092-9096: `Burning` allowed on `InBubble(_) | VesselLatched` — "snapshot: burning node without a body" is the only residence Fat). But the ONLY exit from `SurfaceLatched` — `unlatched_body`, shared by `Unlatch`, `Undock`, and the control commands (lib.rs:3318-3382) — unconditionally executes `v.maneuver = None;` (lib.rs:3369) for BOTH statuses, with an inverted rationale: "a `Burning` one has no executor running: leaving it would strand a zombie node". That rationale is wrong: `drive_node_burn` (lib.rs:8060) runs every bubble tick for any `InBubble` body carrying a `Burning` node, and `unlatched_body` materializes the vessel `InBubble` — a preserved node would resume exactly as documented.
**Impact**: A burn that latches mid-run (e.g., a suicide-burn touchdown that triggers surface capture) is guaranteed to be silently discarded on unlatch — the "resume" path is unreachable because unlatch is the only way out of the latched state. The player loses the remaining Δv intent with no event, no error, and no `fired_events` record; the restore gate meanwhile keeps validating a state class (`Burning` + `SurfaceLatched`) that can never fulfill its documented purpose.
**Suggestion**: In `unlatched_body` (lib.rs:3369), clear only `Scheduled` nodes and preserve `Burning` ones (the executor re-owns throttle/attitude on the next bubble tick). If the drop is truly intended, invert the contracts instead: fix both maneuver.rs doc passages AND make `restore` Fat on `Burning` + `SurfaceLatched` so the dead state class cannot be saved.

### [SEVERITY: MEDIUM] Finding 2: ColonyDelivery contract facts count cargo landed into dead/dormant colonies — a supply contract completes by dumping into an abandoned colony's frozen store
**File**: crates/csp-sim/src/transfers.rs:[1027-1041] (with crates/csp-sim/src/transfers.rs:[1082-1099])
**Problem**: `fire_transfer_complete` records the `colony_deliveries` fact and triggers `ContractTrigger::ColonyDelivery` whenever `t.to` is a colony and `landed > 0.0`, with no liveness check — while `credit_end`'s Colony arm deliberately still credits dead colonies ("a dead or vanished colony still holds its frozen stores, so the credit lands there too").
**Evidence**: `if let TransferEnd::Colony(c) = t.to && landed > 0.0 { ... colony_deliveries.entry((c.0, resource)).or_insert(0.0) += landed; self.contract_notify(&ContractTrigger::ColonyDelivery, ...)?; }` — no `colony_live` gate anywhere in the fact path (the gate exists at apply time only, `joined_colony_gate` transfers.rs:1338, and colony death mid-flight — PowerLost/dormancy/abandon transitions — does not cancel in-flight transfers).
**Impact**: A "deliver X to Colony C" contract is fulfilled by delivering into a colony that died after launch. The terminal-bookkeeping credit is defensible; counting it as the resupply fact that completes contracts is not — the contract's economic meaning (supply a functioning colony) is silently satisfied by a frozen store nobody consumes.
**Suggestion**: Gate the fact on liveness — mirror `credit_end`'s own check: `if let TransferEnd::Colony(c) = t.to && landed > 0.0 && self.colonies.get(&c).is_some_and(|co| crate::colonies::colony_live(&co.state))`. The cargo still lands (totality preserved); only the contract fact skips dead colonies.

### [SEVERITY: MEDIUM] Finding 3: Per-part duplicate-resource tank specs silently break the capacity/contents contract (spawn_contents drops all but the last spec; debit/credit use only the first)
**File**: crates/csp-sim/src/transfers.rs:[399-405] (spawn_contents), [493-497]/[530-534] (debit/credit `.find()`), [331-344] (vessel_capacity sums every spec)
**Problem**: Contents are keyed `(PartNodeId, ResourceId)` but capacity and the mass convention are per tank spec. For a part declaring two `TankSpec`s with the same resource: `vessel_capacity` sums both capacities; `check_tank_masses` requires `mass_kg` to cover both; but `spawn_contents` collects specs into a `BTreeMap<ResourceId, f64>` where the LAST spec silently overwrites the first, and `debit`/`credit` resolve the resource via `part.tanks.iter().find(...)` — the FIRST spec only.
**Evidence**: `part.tanks.iter().map(|t| (t.resource.clone(), t.capacity)).collect()` (BTreeMap dedupe) vs `.filter(|t| t.resource == *resource).map(|t| t.capacity).sum()` vs `part.tanks.iter().find(|t| t.resource == *resource)`. Data-driven crafts are protected upstream (`csp-phys/src/resolve.rs:1294` "duplicate tank capacity resource id"), but `SpawnPhysicalVessel` accepts any programmatic `CraftDef` and `check_tank_masses` does not catch this class, so the divergence enters silently.
**Impact**: For such a part: reported capacity exceeds what any code path can fill (transfers pass the `free < amount` gate then `credit` returns 0 moved), spawn contents understate holdings while `mass_kg` carries the full double wet mass — phantom mass that never drains, and a transfer into the "free" space round-trips or, if the source tanked changed shape meanwhile, units leave the simulation per the fallback rule. All silent.
**Suggestion**: Reject the input up front: in `check_tank_masses` (the spawn gate) reject a part whose `tanks` carry a duplicate resource id, matching the resolver's rule — one `BTreeSet` walk, same `Recoverable` class as the mass check.
