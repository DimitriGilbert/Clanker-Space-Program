# Ruthless Review 15 — csp-app peripheral files (warp, settings_io, audio, synth, bugreport, logring, main, Cargo.toml)

Scope: crates/csp-app/src/{warp.rs, settings_io.rs, audio.rs, synth.rs, bugreport.rs, logring.rs, main.rs}, crates/csp-app/Cargo.toml. lib.rs excluded (reviewed separately). STATIC REVIEW ONLY — no cargo.

### [SEVERITY: HIGH] Finding 1: Warp-up is mathematically unreachable on real scenes — `affordable()` compares ms-per-second against ms-per-frame
**File**: crates/csp-app/src/warp.rs:143-146 (constants at :37-39)
**Problem**: The promotion inequality extrapolates one measured tick to a per-wall-second load (`per_tick_ms × TICK_HZ × k`, units ms/s) and compares it against a per-frame budget (`BUDGET_FRACTION × FRAME_BUDGET_MS` = 0.5 × 16.67 = 8.33 ms, units ms/frame). The units don't match; numerically the rule is 60x stricter than the documented intent ("budget_fraction — the share of the frame budget sim stepping may consume", :35-37).
**Evidence**: `affordable()` at :143: `self.measured_step_ms * TICK_HZ as f64 * WARP_LADDER[idx] as f64 * margin < BUDGET_FRACTION * FRAME_BUDGET_MS`. Promotion to x2 (rung 1, margin 1.5) requires `measured_step_ms < 8.33 / (64 × 2 × 1.5) = 0.0434 ms/tick` (43 µs). The project's own committed perf log (docs/perf/perf-log-devbox-release.ron) measures 0.67 ms/tick (200-part tower), 4.63 ms/tick (1000-part station), 1.0 ms/tick (300-part landed stack) — 15–107x over the threshold. Even x10 rails promotion needs < 8.7 µs/tick. Under the intent-consistent reading (per-frame cost = 0.67 × 64 × 2 / 60 = 1.43 ms < 8.33 ms budget) x2 is trivially affordable. warp.rs's own ladder doc (:10-13) says ×3/×4 unlock "when per-tick cost on the reference machine is ≤ 0.5 ms" — at 0.5 ms/tick the code computes 0.5×64×2×1.5 = 96 > 8.33, so even the authors' stated operating point cannot promote one rung. Internal confirmation: the hysteresis test (:388) had to use `5e-6` ms/tick (5 nanoseconds, mislabeled "5µs" in the comment) because any realistic value fails every rung.
**Impact**: Player-visible: pressing `.` with any real vessel leaves effective warp pinned at ×1 forever — physics warp ×2 AND rails warp ×10…×10⁵ never engage (the only promotion path is `decide()`'s margined streak; nothing else emits `SetWarp` upward). The entire warp feature is dead outside trivial scenes. HUD shows requested > effective with no way to reach it.
**Suggestion**: Make the units consistent per frame: divide the LHS by the frame rate (or multiply RHS by 60): `self.measured_step_ms * TICK_HZ as f64 * WARP_LADDER[idx] as f64 * margin / 60.0 < BUDGET_FRACTION * FRAME_BUDGET_MS` — equivalently `FRAME_BUDGET_MS * BUDGET_FRACTION * FPS`. Replay safety is unaffected (warp level is a logged command, §2.6.3). Note PLAN §2.6.3's inequality text carries the same dimensional error — the plan letter and the plan intent disagree; fix the code to the intent and amend the plan. Also fix the test comment at :385-387 (5e-6 ms = 5 ns, not 5 µs).

### [SEVERITY: MEDIUM] Finding 2: settings save is a truncate-in-place write — crash or ENOSPC mid-save destroys the previous good file
**File**: crates/csp-app/src/settings_io.rs:408
**Problem**: `save_settings_to` writes with `std::fs::write`, which opens the destination with `O_TRUNC` and writes in place. A crash, power loss, or write error partway (e.g. ENOSPC) leaves `settings.ron` truncated or partial — the previous complete settings are gone.
**Evidence**: `std::fs::write(path, text).map_err(|e| format!("settings write {}: {e}", path.display()))` — no temp file, no rename, no fsync. `fs::write` errors are returned to the caller after the destination has already been truncated, so even a handled failure has already destroyed the old file.
**Impact**: Player-visible: a crash during save or a full disk replaces a working settings file with a partial one; the next launch runs the salvage path and loses every field past the truncation point (keybinds, volume, window size). Not a brick (defaults + salvage recover a runnable app), but avoidable user-settings loss — the exact failure class the module's own salvage machinery exists to soften.
**Suggestion**: Write to `settings.ron.tmp` in the same directory, then `std::fs::rename` over the destination (atomic on POSIX and Windows same-volume). Rename-based replace also makes ENOSPC non-destructive: the old file survives a failed save intact.

### [SEVERITY: MEDIUM] Finding 3: Dead audio player is permanent — no re-open after subprocess death, silence until app restart
**File**: crates/csp-app/src/audio.rs:530-543 (open at :415, sole ownership in lib.rs:765)
**Problem**: `AudioBackend::open` runs exactly once at graphics init, and once the player child exits mid-session (`update`'s `try_wait` flips `alive = false` at :532-537), every subsequent `update` returns at :541-543 and nothing ever tries to re-open a player. The fallback/probing machinery (`PLAYERS`, the settle check) exists only on the startup path.
**Evidence**: `if !self.alive { return; }` — and the only assignment to the backend is `self.audio = audio::AudioBackend::open(...)` at lib.rs:765 inside `init_graphics`. Realistic triggers: a pipewire/pulse daemon restart, the player subprocess OOM-killed, an ALSA device disappearing (HDMI unplug makes `aplay` exit), or the settle race at audio.rs:438 (a player that takes >60 ms to fail its server connect — paplay's pulse connect timeout is in seconds — passes the settle check, dies one frame later, and `update` then locks in `alive=false` with the working fallback players never tried).
**Impact**: Player-visible: any transient audio-server hiccup or device change leaves the game silent for the rest of the session — cues, engine rumble, everything — even though re-running `open()` (e.g. after the pipewire restart) would succeed. Users fix it by restarting the whole game.
**Suggestion**: On the liveness-loss transition in `update`, record a retry deadline (e.g. `Instant + 5 s`); when it passes, attempt `AudioBackend::open(&settings)` and swap it in on success (open is already failure-safe and returns `None` quietly, so the retry loop is cheap). That also covers the settle-race case — a backend that dies within the first second gets one silent re-probe.

### [SEVERITY: MEDIUM] Finding 4: Every one-shot truncates its envelope mid-decay — audible click at the end of ignition/contact/breakup cues; EngineCut chirp dives to 20 Hz, not 80
**File**: crates/csp-app/src/synth.rs:80-83, :154-246 (recipes at :156-244)
**Problem**: `decay`'s own doc says a sound is "gone at ~5τ", but no recipe allocates anywhere near 5τ of buffer — the samples are hard-cut while the envelope still stands at 4.6–18% of full scale, which is a step discontinuity straight into silence: the textbook end-of-SFX click.
**Evidence**: End-of-buffer envelope `exp(-len/τ)`: EngineIgnition 0.6 s/τ0.35 → 0.180 (worst: the brown-noise term reaches ~±0.9, so the final sample can step by ~0.1–0.2 full scale); Contact 0.065; Breakup 0.050; UiConfirm 0.050 (a 2.3% step on *every* settings ack); VesselLeftBubble 0.062; VesselRemoved 0.046. Secondary math error in the same file — EngineCut (:174-176) computes its falling pitch as `sine(f(i), i)` with `f(i) = 140 − 60·i/N`; the actual instantaneous frequency of `sin(2π·f(i)·i/SR)` is `f(i) + i·f'(i)`, which ends at 140 − 2·60 = **20 Hz**, not the "140 → 80 Hz" the comment claims — the puff's tail dives into sub-bass instead of the intended gentle sag.
**Impact**: Player-visible: a faint tick/thump on the tail of engine ignition (loudest offender), touchdown contact, and breakup cues, and a soft click after every UI acknowledge; the engine-cut puff pitches down far deeper than designed.
**Suggestion**: Apply a short raised-cosine fade-out over the last ~5 ms of every rendered buffer in `render()` (one loop, applies to all recipes uniformly) — that removes the truncation click without touching the recipes. For EngineCut, use the phase-accumulator `Osc` with `hz` lowered per sample instead of `sine(f, i)`, so the instantaneous frequency is what the comment says.

### [SEVERITY: LOW] Finding 5: Bug-report log tail inherits the console filter — `RUST_LOG=warn` ships a nearly empty `log.txt`
**File**: crates/csp-app/src/logring.rs:27-29, :64
**Problem**: The ring buffer only keeps records that pass env_logger's *console* filter, and `set_max_level(max)` (with `max = inner.filter()`) drops sub-filter records before they even reach `TeeLog`. The tail that exists for §2.14 crash diagnosis is gated by the same knob that controls console verbosity.
**Evidence**: `fn log(&self, record: ...) { self.inner.log(record); if self.inner.enabled(record.metadata()) { push(...) } }` plus `log::set_max_level(max)` in `init()`. With `RUST_LOG=warn` (or `error`), info-level diagnostics — which is what the frame loop, warp demotions, and salvage notes log at — never reach the ring.
**Impact**: A user who has set `RUST_LOG` below `info` (or followed instructions to quiet the console) produces a bug-report bundle whose `log.txt` contains only the warn/error lines — quite possibly empty — silently degrading the artifact the whole module exists to produce. Default-config users are unaffected.
**Suggestion**: Capture the tail unconditionally (or at a fixed `info` floor independent of `env_logger`'s filter): the ring is bounded at 500 lines, so the cost is one `format!` per record that the console dropped — negligible at this game's log rate. Call `set_max_level(LevelFilter::max)` or `Trace` since `TeeLog::enabled`/`inner.log` still apply the console filter per record.

---
## Verdict (5 lines)

1. The peripheral modules are unusually well-engineered — docs tied to PLAN sections, real tests for the genuinely tricky seams (cue multiset edge-detection, hysteresis bound to one rung, demotion rebase, salvage paths), and honest graceful-absence contracts throughout.
2. But the flagship warp controller ships a dimensional error inherited from PLAN §2.6.3's own text: ms-per-second compared against ms-per-frame makes warp-up unreachable at the project's own committed per-tick costs — time warp above ×1 is effectively a dead feature on real vessels (Finding 1, HIGH).
3. The remaining findings are classic polish/robustness gaps with concrete player symptoms: settings loss on crash-during-save, permanent silence after one audio-server hiccup, and a click on every cue because envelopes truncate at 1.7–3τ.
4. bugreport.rs, logring.rs (modulo Finding 5), main.rs, and Cargo.toml are clean — bounded, lock-disciplined, no fake features, no PII beyond one rare warn line that embeds the config path (follow-up: log the file name only).
5. Follow-ups (out of scope): PLAN §2.6.3's inequality text needs the same unit fix as Finding 1; GraphicsSettings.quality remains consumed-by-nothing (tracked as P14-F1, honestly documented).
