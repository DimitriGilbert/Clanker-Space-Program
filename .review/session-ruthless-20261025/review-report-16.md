### [SEVERITY: CRITICAL] Finding 1: Preprocessor recursion — guest source aborts the whole process (stack overflow at `prepare`)
**File**: crates/csp-script/src/lib.rs:[395-413] (`Scan::code` backtick-template branch, `b'$' if b.get(i+1) == Some(&b'{')` → `i = self.code(i + 2, true)? + 1`)
**Problem**: `preprocess` is a *recursive-descent* scanner: every `${` inside a backtick template recurses into `code`, and inside that code a new backtick template with another `${` recurses again. Each `` `${ `` pair in the source adds one native stack frame, with no depth cap anywhere (no counter, no `max_operations` — this runs before Rhai ever sees the source).
**Evidence**: verified empirically with the scanner extracted verbatim (standalone `rustc` build, 2 MiB stack): `` "`${".repeat(20000) `` (a 60 KB script) → `thread has overflowed its stack; fatal runtime error: stack overflow, aborting`. 5,000 reps pass, 20,000 aborts. Default 8 MiB main-thread stack dies around ~4x that (~240 KB source); wasm's ~1 MiB stack dies at ~10k reps (~30 KB).
**Impact**: `RhaiHost::prepare` is called from the `LoadScript` apply (csp-sim lib.rs:6974-6977) — a player- or MCP-supplied script of a few dozen KB of repeated `` `${ `` aborts the entire sim process before Rhai's own protections (parser depth limits, `max_operations`, strikes) can engage. Stack overflow is not `catch_unwind`-able, so this is a full sandbox escape-by-crash of the host, from both the load path and the restore path (`run_tick`'s lazy recompile calls `preprocess` on serialized `source` too, lib.rs:918). A single malicious save file kills the process on load.
**Suggestion**: Make the `${`-descent iterative or depth-capped: thread a `depth: usize` through `Scan::code` and reject nesting > e.g. 64 with a compile error (Rhai's own expr-depth default is 32, so 64 is generous), e.g. `if depth > 64 { return Err("template interpolation too deep".into()); }` at the recursion site. Same treatment for the closing-side walk.
### [SEVERITY: HIGH] Finding 2: Op budget does not bound memory — string/array doubling OOMs the host in ~34 ops
**File**: crates/csp-script/src/lib.rs:[572-587] (`RhaiHost::new` — sets only `max_operations`), vs rhai-1.27.0 `src/api/limits.rs` `Limits::new()` defaults `string_len: None, array_size: None, map_size: None` (verified in the local registry source)
**Problem**: the host's only resource limit is `set_max_operations`. Rhai's memory limits (`set_max_string_size` / `set_max_array_size` / `set_max_map_size`) are never called (grep: zero occurrences in csp-script), so guest strings/arrays/maps are unlimited. Op counting bounds the *number* of operations, not the *work per operation*.
**Evidence**: a three-line guest `fn on_tick(ctx) { let s = "0123456789abcdef"; let i = 0; while i < 60 { s = s + s; i += 1; } }` doubles a 16-char string 60 times for ~a few hundred counted ops — far under the 20 000 budget — while transiently allocating 2^60+16 bytes; the host process is OOM-killed long before the loop ends (16 GB at ~30 doublings). The same trick works with array `arr.push(arr)`-style growth inside the op budget.
**Impact**: the documented sandbox contract ("`set_max_operations` is the only budget" and `TickIo::log_line`'s "the op budget caps per-tick volume") is false for memory: one script tick can exhaust host memory, killing the sim/server process non-deterministically (OOM kill / wasm `MemoryAllocationFailure` trap) — in the determinism domain this is also a *non-deterministic abort*, the worst failure class. On wasm it takes the whole web demo down with it.
**Suggestion**: in `RhaiHost::new`, set memory ceilings alongside the op budget — e.g. `engine.set_max_string_size(1 << 20); engine.set_max_array_size(10_000); engine.set_max_map_size(10_000);` (persist maps are supposed to be "a map of primitives" — 10k entries is generous), and forward them (or fixed fractions of the op budget) in `set_op_budget` if per-save scaling is wanted. Rhai raises `ErrorMemoryTooLarge`-class runtime faults, which the existing fault path already classifies as a strike.
### [SEVERITY: MEDIUM] Finding 3: `ctx.persist = #{...}` is silently dropped — write-back reads the shared cell, and the doc comment claims otherwise
**File**: crates/csp-script/src/lib.rs:[975-979] and [1014-1025]
**Problem**: the persist write-back reads `persist_dyn.flatten_clone().try_cast::<Map>()` — the shared cell inserted into `ctx` before the call. Index writes (`ctx.persist["k"] = v`) mutate through the shared cell and persist. But a wholesale reassignment (`ctx.persist = #{"n": 0}`) only replaces the *local* `ctx` map's entry; the shared cell keeps the old map, and the write-back silently keeps the previous `persist` (the `None => None` arm at 1024, which is in fact unreachable because the cell is always a map).
**Evidence**: the comment at 975-978 states "a non-map result means the script reassigned `ctx.persist` wholesale — also legal, read whatever it left" — but the code path for that case keeps the OLD persist (`persist_next = None` → `script.persist` unchanged at 1046-1048), i.e. the reassignment is discarded, not "read". Nothing faults, nothing logs.
**Impact**: a script using the natural Rhai rebuild idiom (`ctx.persist = #{"phase": 1, ...}`) silently loses all cross-tick state every tick — a phase machine that never advances with no diagnostic, in a subsystem whose stated philosophy is "refused loudly rather than silently degrading in the save" (lib.rs:469-470). The doc comment actively tells script authors the pattern works.
**Suggestion**: pick one honestly: (a) smallest: fix the comment to state the real rule ("only in-place mutation of the shared map persists; wholesale reassignment is ignored") and pin it with a test like the existing `host_runs_on_tick_and_writes_persist`; or (b) detect and fault: impossible post-hoc from the host since the arg map is consumed by `call_fn` — so (a) plus a doc paragraph in the `ctx` contract section (lib.rs:34-52) is the honest fix.

### [SEVERITY: MEDIUM] Finding 4: CI never builds with the pinned toolchain — `@stable` overrides `rust-toolchain.toml` 1.97.1
**File**: .github/workflows/ci.yml:[15] (`dtolnay/rust-toolchain@stable`) vs rust-toolchain.toml:[2] (`channel = "1.97.1"`), Cargo.toml:[7] (`rust-version = "1.95"`)
**Problem**: `dtolnay/rust-toolchain` exports `RUSTUP_TOOLCHAIN` for subsequent steps (set in its `rust-toolchain.sh`), which takes precedence over the repo's `rust-toolchain.toml`. Every CI step (fmt, clippy -D warnings, tests, wasm check, replays, cargo-deny) runs on *latest stable*, whatever that is on the day of the run — not on the pinned 1.97.1.
**Evidence**: the action's shell script sets `RUSTUP_TOOLCHAIN` (action.yml only sets CARGO_* vars; the toolchain selection lives in rust-toolchain.sh). The repo simultaneously pins 1.97.1 in the toolchain file and `rust-version = "1.95"` — three different compilers in play, and the pin is the only one CI never exercises.
**Impact**: for a project whose whole determinism discipline is exact-pin-everything, CI green on stable N says nothing about the pinned 1.97.1 build devs and the demo ship (compiler/LLVM codegen differences can change float-heavy sim results and thus golden hashes); conversely a stable-channel clippy/lint change reds CI with zero repo change. The MSRV claim (1.95) is also never verified anywhere (PLAN §8.2 lists `cargo msrv verify` weekly; no weekly workflow exists — this repo has exactly one workflow).
**Suggestion**: change the CI step to `dtolnay/rust-toolchain@1.97.1` (or pin via the toolchain file only and drop `@stable`), keeping `targets: wasm32-unknown-unknown, components: clippy, rustfmt` as-is. Optionally add the weekly MSRV job PLAN promises.

### [SEVERITY: MEDIUM] Finding 5: The committed `flight-launch` golden is never strictly verified — CI replays only `trivial`
**File**: .github/workflows/ci.yml:[57-58] (`cargo run -p csp-bench --bin csp-replay -- verify data/test-fixtures/trivial`)
**Problem**: the repo ships two frozen golden fixtures — `data/test-fixtures/trivial/` and `data/test-fixtures/flight-launch/` (each with `expected-hash.txt`, `replay.bin`, `fingerprint.json`) — but the strict `verify_golden` path runs only on `trivial`. Grep of all `verify_golden` call sites: the csp-replay CLI (CI, trivial only) and `replay.rs`'s own unit tests (trivial only). The flight-launch eval-suite test (`crates/csp-bench/tests/eval_suite.rs:377-409`) runs the MCP agent flight, not the golden comparison; `committed_eval_suite_all_pass` is goal-based, not hash-based.
**Evidence**: PLAN §8.2's every-commit "Golden replays (fast subset)" row names six scenario classes (ascent, reentry, landing+settle, docking merge, ×10⁵ warp jump, ×1-vs-×10⁵ equivalence, <5 min). The repo implements 2 fixtures and CI exercises 1 — the ascent golden, the one artifact that would catch a physics determinism regression, can drift silently because nothing in CI re-verifies its committed hash.
**Impact**: a determinism regression in ascent dynamics ships unnoticed: the committed `flight-launch/expected-hash.txt` becomes unverifiable decoration until someone happens to run the replay CLI locally. This is exactly the failure mode golden replays exist to prevent.
**Suggestion**: `cargo run -p csp-bench --bin csp-replay -- verify data/test-fixtures/flight-launch` as a second line of the same CI step (it exists and is committed — the cost is one more replay), or a loop `for f in data/test-fixtures/*; do csp-replay verify "$f"; done`. The §8.2 fast-subset scenario list remains unimplemented (reentry/landing/docking/warp fixtures) — that gap is worth an issue of its own, not silent omission.

### [SEVERITY: LOW] Finding 6: api_freeze's rustfmt claim is false — a wrapped signature false-positives the freeze
**File**: crates/csp-script/tests/api_freeze.rs:[11-14] (doc claim), [83-97] (`trait_methods` parses line-by-line)
**Problem**: the header claims "Signatures are compared after whitespace collapse, so rustfmt line-wrapping is not a false positive". `collapse()` only joins whitespace *within a single line*; `trait_methods` collects `fn` declarations one line at a time. If rustfmt wraps `fn request_wake(&mut self, condition: WakeCondition)\n -> Result<u64, SimError>` (trivially triggered by renaming a parameter or a slightly longer type), the parsed fragment is truncated at the line break and mismatches `FROZEN_METHODS` — the test reds on a formatting-only change.
**Impact**: the freeze gate fires "ControlApi drifted — requires a csp.mcp.tools major-version bump" for a non-change, training contributors to edit `FROZEN_METHODS` (the exact drift the test exists to catch) or to suppress the test.
**Suggestion**: join consecutive lines until the signature's terminating `;` before collapsing (`while !line.ends_with(';') { line += next; }`), or parse to the `;` sentinel — then the whitespace-collapse claim becomes true.

## Verdict

The Rhai host's inner mechanics are genuinely good — atomic tick drain with wake-refusal rollback, structured fault classification (no message sniffing), libm shadowing that actually defends against workspace feature-unification, and a no-wall-clock proof test. But the sandbox's *outer* boundary is where it breaks: a 60 KB guest source aborts the whole process in `preprocess` (unbounded native recursion, empirically reproduced), and the op budget places no limit on memory, so string-doubling OOMs the host in ~34 ops — both reachable from `LoadScript` via MCP and from restoring a hostile save, and both contradict the documented budget contract. CI compiles on a moving stable instead of the pinned 1.97.1 and never strictly verifies the committed flight-launch golden. csp-ai's autopilot is deterministic, self-terminating per tick, and matches its documented scope — no findings there. Fix the two sandbox escapes before any build that loads third-party scripts.
