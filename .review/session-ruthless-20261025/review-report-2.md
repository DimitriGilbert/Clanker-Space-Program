### [SEVERITY: HIGH] Finding 1: Production startup never runs the validators — duplicate IDs, dangling refs, and numeric rot load silently
**File**: /home/didi/workspace/Clanker-Space-Program/crates/csp-view/src/lib.rs:800 (consumer), /home/didi/workspace/Clanker-Space-Program/crates/csp-data/src/load.rs:538
**Problem**: Every `csp-data` loader doc defers semantic checks to `crate::validate` ("First def wins on a duplicate id; the validator flags the duplicate loudly", load.rs:533-534, 597-598, 665-666), but the only non-test callers of `validate_*` in the entire workspace are `crates/csp-data/tests/*` and `crates/csp-view/tests/demo.rs:43-91`. The production startup path `View::from_source` (csp-view/src/lib.rs:800-942) loads system/balance/experiments/techtree/sites/contracts/recipes/colonies/parts/resources/loc and installs them straight into the sim with zero `validate_*` calls.
**Evidence**: repo-wide grep for `validate_parts|validate_contracts|validate_system|...` outside csp-data returns only `csp-view/tests/demo.rs` and doc comments. `data_root()` (csp-view/src/lib.rs:2116-2126) resolves `./data` relative to CWD first, so any locally edited or modded tree is loaded verbatim. `LoadedContracts::by_id` (load.rs:667-676), `LoadedExperiments::by_id` (load.rs:599-605), `LoadedRecipes::by_id` (load.rs:535-541) collapse duplicate IDs first-wins with no diagnostic; `sim.set_sites` (lib.rs:871-877) collects into a map where duplicates last-win — two different silent tie-breaks.
**Impact**: `data/` is the invited tuning surface ("ALL tuning lives here"). A tuner who introduces a duplicate part/contract id, a negative `mass_dry_kg`, a NaN balance value, a contract referencing a nonexistent body, or a part referencing an undeclared resource gets no error, no warning — just silently wrong physics/economy at runtime. Field-name typos are caught (deny_unknown_fields), but value rot and reference rot are not. This is exactly the "tuning lies" failure the schema work otherwise guards against, and it contradicts load.rs's repeated "the validator flags it loudly" claims, which hold only in CI.
**Suggestion**: In `View::from_source`, after loading, run the `validate_*` family (they return `Vec<ValidationError>`, cheap at startup: linear passes over tens of files) and fail with a diagnostic listing on non-empty. If startup cost is the worry, gate behind a debug/dev flag, but ship-build silence on semantic rot is not defensible for a data-driven tuning workflow. At minimum, fix the duplicate-ID tie-break asymmetry (pick one of first-wins/last-wins everywhere) and correct load.rs's docs to say the flagging happens in CI only.

### [SEVERITY: MEDIUM] Finding 2: Unbounded zlib inflate in `decode_indexed_png` — decompression-bomb path the code claims is closed
**File**: /home/didi/workspace/Clanker-Space-Program/crates/csp-data/src/biome.rs:235
**Problem**: `decode_indexed_png` enforces the 2048x1024 dimension cap at header parse (biome.rs:207-209) with the comment that "a crafted oversized declaration must not reach inflate (`unfilter_scanlines` would otherwise size its buffers from the attacker's numbers)" — but the inflate itself is uncapped:
```rust
let raw = miniz_oxide::inflate::decompress_to_vec_zlib(&idat)
    .map_err(|_| "IDAT zlib inflate failed")?;
let indices = unfilter_scanlines(&raw, w, h)?;
```
The size check (`raw.len() != stride * h`, biome.rs:255) runs only *after* the entire stream has been inflated into memory. The dimension cap bounds `w`/`h`, not the inflated byte count.
**Evidence**: A PNG with `w=1, h=1` (expected payload: 2 bytes) and an IDAT that inflates to gigabytes (trivially authored: any zlib stream of repeating bytes) passes every header check at biome.rs:183-231, then `decompress_to_vec_zlib` attempts the full allocation before `unfilter_scanlines` rejects it. Reachability: `View::from_source` -> `terrain::config_from_bodies` -> `biome_field` (csp-view/src/terrain.rs:159) decodes the raw `biomes.png` bytes at game startup; `validate_system` (validate.rs:1416) decodes them in CI; the wasm demo embeds the bytes at compile time. A corrupt blob committed as `data/systems/home/terrin/biomes.png` aborts the process with an OOM/ allocation failure instead of yielding `BiomeMapPngInvalid`.
**Impact**: Memory blowup / process abort on a corrupt or malicious biome map in every decode context (game startup, CI, wasm demo). Low security exposure (repo-authored input) but a hard-crash path on data rot, and it directly contradicts the module's own threat-model comment at biome.rs:203-206.
**Suggestion**: `miniz_oxide::inflate::decompress_to_vec_zlib_with_limit(&idat, stride * h)` (available in the pinned 0.8/0.9 workspace versions), keeping the exact-length check afterwards. The cap is already known at that point (`w`, `h` are header-validated).

### [SEVERITY: MEDIUM] Finding 3: `gather_ron_files` follows symlinks — loop = stack-overflow abort, planted link = reads outside `data/`; contradicts `datahash`'s symlink policy
**File**: /home/didi/workspace/Clanker-Space-Program/crates/csp-data/src/load.rs:830-835
**Problem**: The directory walk dispatches on `path.is_dir()`, which follows symlinks:
```rust
let path = entry.path();
if path.is_dir() {
    gather_ron_files(&path, out)?;
} else if path.extension().is_some_and(|ext| ext == "ron") {
```
No symlink check, no depth cap. The sibling walker of the *same tree* — `datahash::collect` (datahash.rs:128-138) — explicitly refuses symlinks ("a symlink inside `data/` is refused rather than silently traversed — its target could change outside the hashed tree ... a link pointing out of `data/` would escape the set entirely"), so the codebase's own threat model treats planted symlinks as in scope; the loader half never got the guard.
**Evidence**: (a) `data/parts/loop -> .` (or any ancestor) makes `is_dir()` true forever -> unbounded recursion -> stack overflow, an abort the `LoadError` contract cannot express. (b) `data/parts/etc -> /etc` traverses the target and pushes every `*.ron` under it — `join_authored` gates authored *names*, not the filesystem itself, so the "reads only under the dir the caller handed it" guarantee in the module doc (load.rs:3-5) is broken by the walker. (c) Same tree, two walkers, two policies: `data_set_hash` errors with `DataHashError::Symlink` while `load_parts` silently follows, so a symlinked data dir hashes as an error but loads as data.
**Impact**: Crash (stack overflow, no diagnostic) or out-of-tree file reads on a data directory containing one bad symlink — plausible from a partial checkout, backup tool, or mod install. Deterministic but undebuggable when it fires.
**Suggestion**: Mirror datahash: use `entry.file_type()` (does not follow) and reject symlink entries with a new `LoadError` variant (e.g. `Symlink { path }`), or at minimum skip them with a logged warning. Either way, make the two walkers agree.

### [SEVERITY: LOW] Finding 4: `colonies.ron` v1 rejected without the documented current+previous band; `LoadError::UnsupportedSchemaVersion` doc is stale
**File**: /home/didi/workspace/Clanker-Space-Program/crates/csp-data/src/load.rs:506 (band), load.rs:117-119 (doc)
**Problem**: PLAN.md §3.1 (line 1011-1013) mandates "the loader supports the current and previous version with explicit defaults; the validator enforces presence", motivated by not breaking community data files. `load_sites_from` honors it with the `SITE_SCHEMA_SUPPORTED = [1, 2]` band (load.rs:483, site.rs:36). `load_colonies_from` passes `&[COLONY_SCHEMA_VERSION]` = `[2]` only (load.rs:506), so a v1 `colonies.ron` (whose shape the const doc at colony.rs:29-33 describes: `Drill { rate_per_s }`, `Converter` with inline pairs) is rejected. Meanwhile the `LoadError::UnsupportedSchemaVersion` doc still asserts "current and previous are supported; only v1 exists today" (load.rs:117-119) — false now that site and colony are at v2 and balance at v11.
**Evidence**: colony.rs:29-33 documents the v1->v2 renames/restructurings; load.rs:506 accepts exactly `[2]`; site.rs:30-36 implements the band for the identical rule. The deviation is undocumented: nothing in colony.rs or load.rs says colonies are exempt from §3.1's band.
**Impact**: No runtime impact on the shipped tree (data/ is at v2), but a mod/community v1 colonies file — the exact constituency §3.1's rule was written for — fails with a version error rather than loading with defaults, and readers of load.rs's error doc get a wrong account of the versioning contract. Since v1->v2 replaced inline rate pairs with the `RecipeId` indirection, defaults cannot reconstruct the old meaning, which makes this arguably a justified exception — but it needs to be stated, not left as an undocumented asymmetry.
**Suggestion**: Either accept `[COLONY_SCHEMA_VERSION - 1, COLONY_SCHEMA_VERSION]` if a sane default mapping exists (it likely does not, per the Converter restructure), or record the exception: a comment on `COLONY_SCHEMA_VERSION` stating "v1 unsupported: the M8-B restructure has no default mapping — §3.1's band intentionally not applied", and update the stale `UnsupportedSchemaVersion` doc text at load.rs:117-119 to describe per-namespace bands instead of "only v1 exists today".

---
## Verdict

High-quality schema layer: `deny_unknown_fields` is complete (verified by scan + the unknown_fields integration tests), error types carry full path context, directory walking is deterministically byte-sorted and consistent with `data_set_hash`, the PNG unfilter is spec-correct integer code, and there are no fake loaders or swallowed IO errors. The gaps are all at the trust boundary: semantic validation exists but nothing in production runs it (so tuning rot loads silently), the inflate that the biome decoder's own comment claims is guarded is not, and the directory walker ignores the symlink threat its datahash sibling handles. Fix the wiring (run validators at startup), cap the inflate, and align the two directory walkers; the rest is polish. Schema/loder fundamentals: 9/10; runtime data-path hardening: 5/10.
