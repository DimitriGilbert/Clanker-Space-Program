### Finding 1: Preprocessor recursion — stack overflow at `prepare` — CONFIRMED
**Original**: Uncapped `preprocess` recursion on `${` in backtick templates aborts the process before the sandbox engages; reachable from LoadScript + save-restore.
**Verification**: crates/csp-script/src/lib.rs:299 `preprocess` -> `Scan::code(0, false)`; lib.rs:402-404 backtick-template branch recurses `i = self.code(i + 2, true)? + 1` on every `${`. `fn code(&self, mut i: usize, brace_stop: bool)` (lib.rs:321) carries NO depth parameter — grep confirms `self.code(` has exactly one call site (lib.rs:404), no counter anywhere. Nesting: each `` `${ `` pair enters template scan then recurses into `code`, which on the next `` ` `` re-enters the template branch -> unbounded native stack growth. Reachability: `RhaiHost::prepare` (lib.rs:895-896) calls `preprocess(source)?` BEFORE `engine.compile` (897); `apply_load_script` calls `engine.prepare` (csp-sim/src/lib.rs:6975-6977, dispatch at 4679 `SimCommand::LoadScript`); restore path recompiles serialized source via `preprocess(&script.source)` (lib.rs:918). No source-length cap anywhere: ingress caps encoded commands at 64 KiB (csp-server/src/ingress.rs:27,141-143) — still enough nesting to exceed a 2 MiB thread stack per the report's repro; and restore validation `script_state_is_valid` (csp-sim/src/scripts.rs:596-598) checks only persist values, never the source — a hostile save of any size reaches preprocess on load. No `thread::Builder`/`stack_size` in csp-script (runs on caller's thread). csp-server serves via tokio (serve.rs:147 `tokio::spawn`), whose worker threads default to 2 MiB stacks — the empirically-overflowing configuration. No depth cap = confirmed; severity CRITICAL stands (stack overflow is uncatchable, pre-sandbox).
### Finding 2: Op budget does not bound memory — string doubling OOM — CONFIRMED
**Original**: `RhaiHost::new` sets only `max_operations`; rhai 1.27.0 leaves string/array/map sizes unlimited → OOM in ~34 ops.
**Verification**: rhai pinned `=1.27.0`, `default-features = false, features = ["no_std"]` (workspace Cargo.toml:45; `unchecked` deliberately NOT enabled — csp-script lib.rs:23, Cargo.toml:35, so limits are live). rhai engine.rs:296 `Engine::new()` sets `limits: Limits::new()`, and limits.rs:111-115 defaults `string_len: None, array_size: None, map_size: None` (verified in local registry ~/.cargo/registry/src/.../rhai-1.27.0/src/api/limits.rs). csp-script sets ONLY `set_max_operations` (lib.rs:575 in `new`, lib.rs:1077 in `set_op_budget`) — grep across the whole workspace finds zero calls to `set_max_string_size`/`set_max_array_size`/`set_max_map_size`. The guest's string `+` is `MoreStringPackage::add_append` (string_more.rs:23-38), part of StandardPackage (pkg_std.rs:30), available under `no_std`: each call clones the buffer and appends (line 33-34) — `s = s + s` doubles transient allocation per counted op; 30 doublings of a 16-char string = 16 GiB, ~120 ops total vs DEFAULT_SCRIPT_OP_BUDGET = 20_000 (csp-sim/src/scripts.rs:94). Array growth via push is equally uncapped. Doc claim "set_max_operations is the only budget" (lib.rs:32) is accurate but the memory hole is real: HIGH stands.
### Finding 3: `ctx.persist = #{...}` wholesale reassignment silently dropped — CONFIRMED
**Original**: Persist write-back reads the shared cell; wholesale `ctx.persist = #{...}` reassignment is silently discarded while the comment claims it is "read".
**Verification**: crates/csp-script/src/lib.rs:953 `persist_dyn = Dynamic::from_map(...).into_shared()`; :961 `ctx.insert("persist", persist_dyn.clone())`; :972 `call_fn(..., (ctx_dynamic,))` passes ctx by value — in-place index writes (`ctx.persist["k"] = v`, the pattern the existing test at lib.rs:1265-1283 exercises) mutate through the shared cell, but `ctx.persist = #{...}` replaces only the local arg map's entry. Write-back :979 `persist_dyn.flatten_clone().try_cast::<Map>()` reads the ORIGINAL shared map; `None => None` (:1024) then skips assignment at :1046-1048 — `script.persist` keeps the previous value. No fault, no log. The comment at :975-978 ("a non-map result means the script reassigned ctx.persist wholesale — also legal, read whatever it left") does not match the code: nothing "reads what it left", and the `None` arm is effectively unreachable since the shared cell is always a map. Natural rebuild idiom (`ctx.persist = #{...}`) loses all cross-tick state silently — contradicts the module's own "refused loudly rather than silently degrading" stance (lib.rs:467-470). MEDIUM stands; suggested fix (a) — correct the comment + doc, pin with a test — is the right shape since detection post-call is impossible (arg consumed by call_fn).
### Finding 4: CI stable toolchain bypassing pinned 1.97.1 via RUSTUP_TOOLCHAIN — DISMISSED
**Original**: `dtolnay/rust-toolchain@stable` exports RUSTUP_TOOLCHAIN which overrides rust-toolchain.toml, so CI never builds with pinned 1.97.1.
**Verification**: The claimed mechanism does not exist. Fetched the action's `stable` branch (b725eda, 2026-10-16) action.yml directly from GitHub: it contains NO occurrence of RUSTUP_TOOLCHAIN (grep exit 1); toolchain selection is `rustup toolchain install "$toolchain"` + `rustup default "$toolchain"` (action.yml steps "rustup toolchain install" and "rustup default"). The report's cited `rust-toolchain.sh` file has NEVER existed in the repo's history (`gh api .../commits?path=rust-toolchain.sh` returns empty; the first composite version f51b131c, 2021, already used `rustup default`). Rustup's documented override precedence (rust-lang.github.io/rustup/overrides.html): `+toolchain` shorthand > RUSTUP_TOOLCHAIN env > **rust-toolchain.toml file** > directory overrides > default toolchain. Since the action only sets the *default*, every cargo step in the repo (rust-toolchain.toml channel="1.97.1") resolves to 1.97.1 — CI DOES exercise the pin (rustup auto-installs a missing pinned toolchain on modern runners; if it could not, it would hard-error, never silently fall back to stable). Residual truth: no MSRV job exists (PLAN.md:1761,1853 promise weekly `cargo msrv verify`; only ci.yml exists) — a missing-feature nit, not the claimed wrong-compiler MEDIUM. Suggested fix `@1.97.1` remains a harmless belt-and-braces tidy-up.

### Finding 6: api_freeze rustfmt claim is false for wrapped signatures — CONFIRMED (nuance on trigger)
**Original**: `collapse()` only joins whitespace within one line; `trait_methods` parses line-by-line, so a rustfmt-wrapped signature truncates at the line break and false-positives the freeze.
**Verification**: crates/csp-script/tests/api_freeze.rs:11-14 claims "Signatures are compared after whitespace collapse, so rustfmt line-wrapping is not a false positive"; but `collapse` (:66-68) is `split_whitespace().join(" ")` on the passed string and `trait_methods` (:83-97) iterates `body[..end].lines()` taking only the single line that starts with `fn ` — a wrapped `fn request_wake(\n &mut self, ...` yields rest=`"("` and mismatches FROZEN_METHODS[:33]. Currently latent: the trait's fn lines (csp-script/src/lib.rs:82-102+) are all single-line and fit rustfmt's default 100 cols (longest ~83), no rustfmt.toml in repo. Nuance vs the report: the report's example trigger ("renaming a parameter") is wrong — parameter names ARE pinned in FROZEN_METHODS, so a rename trips the freeze by design, wrapping or not; the real false-positive triggers are a max_width config change or a rustfmt version changing wrap decisions (formatting-only change reds the test). LOW stands: doc claim untrue of the parser; the suggested fix (join lines to the terminating `;`) makes the claim real.
