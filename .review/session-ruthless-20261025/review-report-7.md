### [SEVERITY: HIGH] Finding 1: The tech tree gates nothing — the unlock gate and upgrade freeze have zero production callers
**File**: crates/csp-sim/src/tech.rs:71-73, 108-130, 315-327; crates/csp-sim/src/lib.rs:5122-5294; crates/csp-sim/src/manufacture.rs:111-245
**Problem**: `TechState::is_part_unlocked` is documented as "the part availability gate the editor and manufacture share", and `World::build_part` as "the manufacture helper a craft-build flow calls" — but the only callers of either outside `tech.rs`'s own tests are none. Verified by grep across `crates/` and `apps/`: zero hits in `csp-view`, `csp-app`, `csp-ui`, or any non-test code. Both real craft-entry paths bypass tech entirely:
- `apply_spawn_physical` (the LAUNCH button path, csp-view/src/lib.rs:1872) checks physics, cap, finiteness, tank masses, part_costs, funds, occupancy — never tech.
- `apply_manufacture_craft` checks site/BOM/funds/cap/weld — never tech.
- `launch_preflight` (csp-view/src/lib.rs:2034-2071) checks cap, funds, occupancy — never tech.
**Evidence**: The gate is not merely unwired, it is *unwirable* at this boundary: `CraftDef.parts: Vec<WeldPart>` carries no `PartId`/`BuiltPart` identity (see the test fixture, manufacture.rs:422-451), so the sim cannot map a spawned craft back to `PartDef.tech_requirement`. Consequently purchased `UpgradeTrack` levels also never reach any real craft: `frozen_upgrades`/`compose_upgrade_levels` feed only `build_part`, which nothing calls; VAB sessions build `BuiltPart`s with empty `upgrade_levels_at_build` (csp-phys/src/resolve.rs:280 default) and no access to `TechState`. PLAN.md:1116 ("Upgrades apply at manufacture, frozen into `BuiltPart.upgrade_levels_at_build`") and the M7 milestone row ("tech tree + upgrade tracks wired into the M3 resolver (frozen at build)", PLAN.md:1498) are satisfied only by dead code.
**Impact**: A player (or any script via the public `SimCommand` queue — `SourceClass::Script` is a first-class source, lib.rs:402) launches or manufactures any part regardless of research state; science spent on `ResearchTech`/`ResearchUpgradeLevel` is a pure sink with zero gameplay effect — the entire M7 progression system is decorative in the live loop.
**Suggestion**: Enforce at the sim boundary, which requires identity: extend `CraftDef` (or the commands) to carry per-node `part_id` + `upgrade_levels_at_build` records produced by `World::build_part`, and have `apply_spawn_physical`/`apply_manufacture_craft` re-verify each node's `tech_requirement` against `tech.researched` (and reject `upgrade_levels_at_build` exceeding currently-purchased levels). Until then, fix the docs on `is_part_unlocked`/`build_part` to say the gate is sim-library-only, not enforced.

### [SEVERITY: MEDIUM] Finding 2: `RecoverVessel` silently destroys running-lab WIP — accrued science vanishes, escrowed data is lost
**File**: crates/csp-sim/src/economy.rs:921-976; crates/csp-sim/src/lib.rs:4263-4275; crates/csp-sim/src/research.rs:572-597
**Problem**: `apply_recover_vessel` banks only *pooled* data (`v.science.data`), then calls `remove_vessel`, which calls `research::drop_vessel_projects` — "work-in-progress is lost, no accrual". That no-accrual rule is documented in research.rs's module doc for *destruction* ("the lab burned"); recovery of an intact landed vessel hits the same path. Data escrowed into a project was removed from the pool at `StartResearch` (research.rs:1031-1034), so it is invisible to the recovery banking loop and dies unbanked; the project's accrued-but-unbanked science dies with it.
**Evidence**: economy.rs:922-945 iterates `v.science.data.values()` only; lib.rs:4269-4275 `research::drop_vessel_projects(...)` drops the records with no accrual; `World::science_at` (research.rs:619-627) counts project accrual in the public live total, so the player-visible science total *decreases* the moment they recover a vessel with a running lab.
**Impact**: Recovering a vessel mid-research loses both the escrowed data units and all accrued science since project start, with no event, no error, and no ledger trace — and `science_now()` visibly regresses, which reads as a sim bug to any player watching the counter. There is also a secondary inconsistency: `closable` (economy.rs:938-942) refuses to close a key held by a live project, yet the project is then dropped anyway and the key stays open forever with its data gone.
**Suggestion**: In `apply_recover_vessel`, finalize the vessel's projects before `remove_vessel` (accrue to the current tick via `finalize_project`, credit the milestone payout, and let the unconverted remnant ride the same recovery fraction as pooled data — or bank it at 100% since the physical sample is coming home). At minimum, reject `RecoverVessel` while a live project rides the vessel, mirroring the `apply_recover_data` guard.

### [SEVERITY: MEDIUM] Finding 3: A mid-build site removal silently eats a paid build order — no refund, no event, and the site inventory is deleted with it
**File**: crates/csp-sim/src/manufacture.rs:252-267; crates/csp-sim/src/economy.rs:648-658
**Problem**: `ManufactureCraft` is a reservation: funds (`FundsReason::Manufacture`) and site BOM inventory are spent at order time. But `fire_construction_complete` handles a vanished site def by dropping the record and returning `Ok(())` — "the delivery drops with the record (total: an event never fails)". `set_sites` (a public, un-gated API) reconciles both the def table and the state arena: `states.retain(|id, _| defs.contains_key(id))` deletes the site's `SiteState` too. There is no `CancelBuild` command, so no path ever refunds an order — the only "abort" is this silent eat.
**Evidence**: manufacture.rs:261-265 `if !self.site_defs.contains_key(&b.site) { return Ok(()); }` — the already-charged craft cost and BOM are gone with no credit, no `FundsReason` entry, no fired event. economy.rs:648-658 `set_sites` drops defs and state rows alike; nothing checks `self.builds` for orders referencing removed sites.
**Impact**: A `set_sites` call after a save-restore with a changed data set (or any programmatic re-install) destroys player funds and stockpiled resources with zero feedback; the player's craft never arrives and the ledger shows only the original debit. Atomicity rule "debit without credit on failure" is violated on this path.
**Suggestion**: On the vanished-site branch, refund the order: credit `craft_cost_micros(craft)` under a new `FundsReason` (or `Manufacture` with positive delta) and re-credit the BOM to... nowhere (site is gone) — so at minimum refund funds and fire a notifying event. Better: make `set_sites` refuse (`Recoverable`) to drop a site that live `ActiveBuild`s reference, or auto-cancel-and-refund there.

### [SEVERITY: MEDIUM] Finding 4: Cross-check CONFIRMED — the economy imposes no cap on the contracts instant-completion faucet (C6's contracts.rs:812-816)
**File**: crates/csp-sim/src/economy.rs:486-495, 669-680; crates/csp-sim/src/contracts.rs:806-816, 1033
**Problem**: C6 reported an unbounded faucet at contracts.rs:812-816 (an offer whose objective is already met completes at acceptance: advance + completion credit in the same apply). Cluster 7's cross-check: does the economy cap it? No. Every contract credit funnels through `World::credit_funds` → `credit`, whose only bound is `funds_micros.saturating_add` at `u64::MAX` (~9.2e18 micros). There is no per-reason cap, no per-tick income limit, no completion-cooldown state in `EconomyState`.
**Evidence**: economy.rs:490 `e.funds_micros = e.funds_micros.saturating_add(micros);` — the entire guard. Worse, line 491-493 clears `insolvent` on any positive credit, so the faucet also instantly launders the bankruptcy state.
**Impact**: Confirms C6's finding is uncapped on the money side: an accept-complete-again loop mints `advance + completion` funds per iteration up to u64 saturation, and the §3.5 "2–5% drain per sim-month" band (PLAN.md:1201-1204) is meaningless against it.
**Suggestion**: The root fix belongs in contracts (C6). Economy-side hardening worth doing anyway: cap per-tick credit under `ContractCompletion`/`ContractAdvance` (or count completions per template per period in `EconomyState`, hashed), and only clear `insolvent` on credits above the outstanding shortfall, not any positive credit.

### [SEVERITY: LOW] Finding 5: PLAN contradiction — unpaid salaries promise `StaffAttrition`/`FacilityDormant` events that do not exist anywhere
**File**: crates/csp-sim/src/economy.rs:66-76 (module doc), 686-708; PLAN.md:1195-1198
**Problem**: PLAN.md:1196-1197: "funds clamp at zero; unpaid salaries trigger `StaffAttrition` and `FacilityDormant` events; an `Insolvent` state is a `Clamping` event that auto-demotes warp to ×1 and notifies." The economy implements only the `Insolvent` event (which, per csp-app/src/lib.rs:904-951, does demote warp). `StaffAttrition` and `FacilityDormant` have zero occurrences in the entire workspace (grep across `crates/`, `apps/`, `xtask/`); economy.rs's own module doc quotes the PLAN sentence but silently drops the two attrition events, so there is no marker that they were deferred.
**Impact**: Insolvency has no teeth beyond a notification: a broke program keeps its full `Active` roster forever with zero salary paid and zero consequence — the "warping to a transfer window can drain you" pressure §3.5 is built around never materializes. Doc-vs-code drift misleads the next implementer.
**Suggestion**: Either implement `StaffAttrition` (retire/un-Active roster members on repeated insolvency — the `CrewStatus::Retired` variant already exists unused) or annotate the module doc + PLAN with the deferral and the milestone that owns it.

## Cleared after verification (no finding)
Currency math is genuinely solid: integer micros end-to-end, one documented float boundary (`to_micros`), clamp-at-zero with a once-per-insolvency `Insolvent` event, affordability pre-checked on both action paths (hire, manufacture) so no debit-without-credit on rejection. Salary grid is absolute and partition-independent (tested). Research escrow accounting is double-count-free by construction (`accrued = η·(D0 − D(t))`, finalize banks accrual only); the soft-cap integral reproduces the plan's quoted sequence; the closed-key invariant is guarded in both directions. Manufacture cost is frozen at order time (no stale-price window), vessel-cap reservation is honored by every growth path (`vessel_slots_in_use` counts builds), id counters are `checked_add` and serialized, `ticks_for` saturation is safe, and negative mass is rejected upstream by `check_tank_masses`. Determinism discipline holds in all four files: BTree containers throughout (including `PartGraph.nodes`, so the f64 mass sum in `craft_mass_kg` has fixed order), libm-only math, fixed draw order. `credit_qualification` is not dead code — reliability.rs and lib.rs write it.

## Verdict (5 lines)
1. The economy core (micros ledger, salary grid, insolvency, recovery payouts) is the strongest code in this cluster — correct, atomic, and honestly deterministic.
2. The tech tree is the weakest: a fully implemented, well-tested module that the actual game loop never consults — its gate, its upgrade freeze, and its doc claims are all currently fiction (Finding 1).
3. Research accrual math is clean, but the recovery path quietly contradicts it by destroying lab WIP (Finding 2).
4. Manufacture's reservation model is sound except the one silent-eats path with no refund (Finding 3).
5. Net: economy/research/manufacture are near-ship; tech enforcement needs real wiring (schema change to carry part identity), not tests.
