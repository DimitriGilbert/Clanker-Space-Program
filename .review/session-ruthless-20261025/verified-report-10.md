### Finding 1: ConfigMask 64-node positional cap — CONFIRMED (mechanics) with impact correction: MEDIUM -> LOW
**Original**: ConfigMask is a u64 over node positions; `active(i>=64)` is always true, writers skip bits >= 64 with no warning, so on >64-part crafts config changes at position >= 64 are silently dropped and a jettisoned fairing keeps shielding/dragging forever.
**Verification**:
- Mechanics all confirmed verbatim. crates/csp-phys/src/aero.rs:189-194: `if i >= 64 { return true; }`. Writers skip the bit: crates/csp-sim/src/lib.rs:6342-6346 (`&& j < 64`), crates/csp-sim/src/joints.rs:1045-1048 (`if j < 64 { mask |= bit << j; }`), plus the same pattern at lib.rs:10183 (node-destroy remap). No warning/log anywhere: `apply_set_aero_config` (lib.rs:6041-6110) has no position-range check; the cap is documented only in code comments.
- Position ordering confirmed: rank in ascending PartNodeId (BTreeMap key order) — `collect_active` iterates `graph.nodes.iter().enumerate()` (aero.rs:956-959) and `if !mask.active(i) { continue; }`; the remaps build explicit ascending-position maps. Not insertion order.
- >64-part crafts are real: csp-bench builds 200- and 300-part crafts (scenarios.rs:700, 799), `merge::tests::thousand_part_station_merges_into_one_body` passes, native VAB `part_limit` defaults to None (csp-ui/src/vab.rs:446) — only the web demo caps at 60 (csp-view/src/demo.rs:25, < 64). PLAN.md:321/1497 confirm the 1000-part station target.
- IMPACT CORRECTION (why the claimed player scenario is unreachable today): (a) `SimCommand::SetAeroConfig` has NO production issuer — repo-wide it is constructed only in csp-sim tests (lib.rs:13034-13070); grep across csp-view/csp-app/csp-script/csp-ui finds zero. Deployable state is explicitly not implemented at v1 (reliability.rs:71). (b) Production fairing jettison goes through `JettisonPart` -> `apply_jettison_part` (lib.rs:6121+), which REMOVES the node from the graph, resets `v.aero_mask = ConfigMask::ALL` (lib.rs:6218), drops the whole aero cache (`p.aero.remove(&vessel)`, lib.rs:6255), and rebuilds via `ensure_aero` (lib.rs:6257) — the mask is not involved, so "the fairing keeps shielding the payload forever" is false for the actual jettison path; shielding follows the graph and the rebuild excludes the removed node. (c) The remap writers' >=64 skip is only observable if the source mask has cleared bits; every production origin is `ConfigMask::ALL` (manufacture.rs:319, life_support.rs:534, economy.rs:1064, colonies.rs:4157, lib.rs:5018/5221/5279/6463/...), and ALL-remaps yield semantic ALL on any craft size.
- Net: a real API/design limitation — the implementation is positional over ALL nodes while PLAN.md:352 specifies "bitset over deployable/jettisonable parts", and the missing >= 64 warning is a genuine trap for the planned deployable work (M4a/M9) — but it is latent, not player-visible in the current product. Recommend keeping the finding with severity LOW and rewording the impact away from fairing jettison (which rebuilds tables) toward "future SetAeroConfig callers on >64-part crafts".

### Finding 2: cm_alpha unvalidated mach_idx reads wrong AoA pair in-bounds — CONFIRMED
**Original**: `cm_alpha(mach_idx)` has no bounds validation; mach_idx >= 5 lands in-bounds on a different AoA pair, silently returning a wrong derivative.
**Verification**: crates/csp-phys/src/aero.rs:808-812 confirmed: `i0 = mach_idx`, `i1 = AERO_MACH_KNOTS.len() + mach_idx`, direct indexing, no check. Layout confirmed: `AERO_MACH_KNOTS: [f64; 5]` (aero.rs:126), `AERO_AOA_KNOTS_RAD: [f64; 6]` (aero.rs:132), `cm_knots` built AoA-major/mach-minor in nested loops (aero.rs:1351-1354), 30 entries (aero.rs:1312, 1346). So mach_idx=6 reads cm_knots[6] (AoA row 1) and cm_knots[11] (AoA row 2) — the slope between AoA rows 1 and 2, exactly as reported. Boundary nit in the original: in-bounds-but-wrong holds for mach_idx 5..=24; the panic starts at mach_idx >= 25 (i1 = 30 out of bounds), not 26. Callers today: tests only (aero.rs:2010, 2028, 2031), consistent with the finding's "no production caller yet". LOW is correct; the suggested `debug_assert!`/typed guard and named stride constant remain valid.

### Finding 3: thermal step discards the overheat list when any node diverges — CONFIRMED (narrower than claimed)
**Original**: if any node's Euler update is non-finite, `step` returns Err and the whole `overheated` vec is discarded; a persistently divergent net permanently suppresses the §3.4 explosion trigger for healthy parts.
**Verification**: crates/csp-phys/src/thermal.rs:369-394 confirmed: crossings accumulate per-node, but `diverged = true` on any non-finite `new_t` returns `Err(Recoverable)` at 389-393, discarding the list including already-detected crossings. The caller confirms the suppression: lib.rs:3771-3786 substitutes `Vec::new()` for `hot` on Err, and `hot` is the sole deterministic §3.4 overheat-destruction feed (lib.rs:3828-3833, `failures[vid].1.extend(hot)`); the withheld node keeps its finite pre-tick temp (thermal.rs:383-387) so persistent divergence repeats every tick. Two reachability notes, both making it narrower than the original text: (1) the weld re-validates every part's thermal def — positive-finite heat_capacity, max_temp_k, emissivity in (0,1] (weld.rs:466-476+) — and `joint_conductance` returns 0 on non-positive inputs (thermal.rs:401-406), so the divergent net needs finite-but-extreme values that overflow the arithmetic (e.g. conductance overflow at k ~ 1e308, `t*t*t*t` overflow), not merely "bad defs"; (2) save restore validates temps are finite and >= 0 and the net is always re-welded (never serialized), so the "corrupt-save net" route requires a part def that slips past both csp-data validation and the weld gate. Also note healthy overheated parts' temps ARE still written (the loop writes each node as it goes), so the reliability `Overtemperature` hazard path (reliability.rs:1355+, reads `temp_fraction = temp/max`) still sees them — only the deterministic explosion trigger is suppressed. LOW confirmed.

### Finding 4: merge_graphs effective_base precondition is debug_assert-only — CONFIRMED
**Original**: `effective_base >= max(primary effective_index)+1` is guarded only by `debug_assert!`; release builds silently alias secondary nodes onto primary WeldParts.
**Verification**: crates/csp-phys/src/merge.rs:235-241 confirmed verbatim — the debug_assert is the only guard, and `debug_assert!` compiles away in release. The module's own doc (merge.rs:230-234) admits the failure mode ("silently aliases secondary nodes onto primary WeldParts, which no check downstream can see") while every other malformed input is a typed `MergeError` (merge.rs:197-199, 208-229) — the inconsistency is real. Notably, the exact predicate the assert checks (`primary.nodes.values().all(|n| n.effective_index < effective_base)`) IS computable from the signature (`primary` is a parameter), so the doc's "cannot be detected here" only applies to the stronger parts-slice-length property; promoting this predicate to `MergeError::EffectiveBase` is zero-cost as suggested. Latency confirmed: the sole in-tree caller (joints.rs:883-891) passes `u32::try_from(craft_p.parts.len())`, and parts.len() only grows (jettison leaves orphan entries, lib.rs:6125-6130), so the invariant holds today. LOW confirmed.
