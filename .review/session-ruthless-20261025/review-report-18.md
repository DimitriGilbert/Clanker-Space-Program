## Findings

### [SEVERITY: HIGH] Finding 1: The flight-launch golden — the only artifact exercising physics/warp/recovery — is never verified by anything
**File**: .github/workflows/ci.yml:57-58 (consumer), crates/csp-bench/src/replay.rs:1080-1129 (in-crate coverage)
**Problem**: CI's sole golden step is `cargo run -p csp-bench --bin csp-replay -- verify data/test-fixtures/trivial`. `data/test-fixtures/flight-launch/{replay.bin,expected-hash.txt,fingerprint.json}` are committed (blessed Oct 24) but no test, bin, or CI step ever reads them: `verify_golden` is referenced only by `csp-replay verify` (CI passes it only `trivial`) and by replay.rs's own tests, which use `trivial_dir()` exclusively. `scenarios.rs`'s flight test builds a fresh world via `flight_initial` — it never touches the committed artifact. Grep across `crates/*/tests`, `apps/`, and `xtask/` confirms no other caller.
**Evidence**: ci.yml comment admits the scope: `# §8.2 golden replays — the M0 fast subset is one scenario.` — but PLAN §8.2's per-commit fast subset is "ascent, reentry, landing+settle, docking merge, ×10⁵ warp jump, ×1-vs-×10⁵ equivalence". The trivial golden is 4 `SetWarp`/`AdvanceTo` commands on a vessel-free `World::new()`.
**Impact**: The strongest determinism artifact — the launch→orbit→rails→reentry→latch→`RecoverVessel` arc that exercises the physics backend, warp spans, SOI/rails transitions, and economy payout — can silently rot. `record`'s self-check ran once at bless time; any replay-path regression since (or a corrupted/truncated committed `replay.bin`) ships undetected while CI stays green on the 4-command golden. The committed flight-launch artifacts are dead weight that *looks* like coverage.
**Suggestion**: Add a workspace test in csp-bench iterating `scenarios::SCENARIOS` and running `verify_golden(&fixtures_root().join(name))` for each (the suite is 2 scenarios today, well under the §8.2 "<5 min" bound), or make the CI step a loop over `csp-replay list`. Pin the count so a recipe without a committed golden also fails.

### [SEVERITY: HIGH] Finding 2: Perf budgets are never enforced at their written values — 400x debug slack in the only profile CI runs, no nightly, no regression baseline
**File**: crates/csp-bench/src/perf.rs:992-1003 (bound), :1053-1056 (claim), :336-383 (run_perf_log)
**Problem**: The only automated execution of the §5.3 budget checks is `cargo test --workspace` (debug). In debug `bound()` multiplies every budget by **400**: `if strict { row.budget } else if cfg!(debug_assertions) { row.budget * 400.0 }`. So CI's effective assertion for `sim.200-part-atmo` is <200 ms/tick against a 0.5 ms budget. Even the release non-REF path is 4x. The release strict bound runs only when `CSP_PERF_MACHINE=ref-*` is manually set. `csp-perf` is run by no CI job (only one `ci.yml` job exists; no nightly workflow anywhere in the repo), and `run_perf_log` has no baseline-comparison code at all — PLAN §8.2's "CPU perf budgets ... fail on >10% regression | nightly" gate is unimplemented machinery.
**Evidence**: perf.rs test doc claims `Each measurement resolves ... the CI-HOST gate the nightly job asserts` — no nightly job exists. The single committed artifact `docs/perf/perf-log-devbox-release.ron` already records `sim.200-part-atmo` FAIL (0.672 > 0.5) and `sim.1000-part-orbit` FAIL (4.63 > 2.0) with no consequence anywhere.
**Impact**: The harness can hide arbitrary CPU regressions: a 100x slowdown of the 1000-part tick passes CI (debug bound 800 ms/tick); the "committed perf log" gate is decorative — two rows are over budget right now and nothing is red.
**Suggestion**: (1) Add a release-mode job (`cargo test -p csp-bench --release perf`) so the 4x diagnostic bound is the loosest thing that runs; (2) implement the §8.2 regression gate: a function diffing `run_perf_log()` output against the last committed log (fail >10% on CPU rows) and run it nightly; (3) in debug, print the measurement and assert only finiteness instead of a 400x bound, so the number in the assertion can't be mistaken for the budget.

### [SEVERITY: MEDIUM] Finding 3: Lockstep transcript ticks are off by one vs the command-log stamps the artifact exists to correlate with
**File**: crates/csp-bench/src/agent.rs:276, 102-104, 362
**Problem**: `Lockstep::step` labels every transcript entry `tick = clock + 1` (`let tick = self.world.clock().ticks().saturating_add(1)`), and `record_rejections(tick, ...)` labels rejections the same way. But the drain stamps commands at the *pre-advance* clock N: `csp-sim`'s `drain_boundary` calls `drain_at(self.clock.ticks(), ...)` (crates/csp-sim/src/lib.rs:6528-6541), so commands an agent enqueues at poll time land in the §7.6 command log stamped N, while the transcript entry carrying them says N+1. The code itself knows it: three lines later `accumulate_dv(tick - 1, report.reached_tick)` passes `tick - 1` as the pre-drain boundary.
**Evidence**: Field doc claims `tick` is "The sim tick the boundary drained at (`clock + 1` at poll time)" — the drain happens at clock N, not N+1. Module doc sells the transcript as "enough to reconstruct *what the agent decided*, while the sim side replays through `csp-replay`'s command log" — correlating the two artifacts now requires knowing an undocumented +1 shift.
**Impact**: Anyone (or any tool) replaying a transcript against a csp-replay command log mis-attributes every decision and rejection by one tick. The lockstep_determinism tests never notice because both runs carry the same wrong tick.
**Suggestion**: Record the stamp tick (`clock.ticks()` at poll time, i.e. `tick - 1`) in `TranscriptEntry` and in the `rejected`/`<drain>` entries, or if the post-boundary tick is intentional, rename the field (`post_tick`) and fix the doc to state the +1 relationship to §7.6 stamps.

### [SEVERITY: MEDIUM] Finding 4: Determinism fingerprint omits rhai — a scripting-engine bump reds goldens with "nothing changed"
**File**: crates/csp-bench/build.rs:19-25 (TRACKED_DEPS), crates/csp-bench/src/replay.rs:58-87 (Fingerprint)
**Problem**: The §7.1 fingerprint tracks `parry3d-f64`, `rapier3d-f64`, `libm`, `rand_chacha`, `blake3` — but not `rhai`. Rhai is squarely in the determinism domain: scripts are hashed sim state (`state_hash` walks "the script book"), their `on_tick` float arithmetic (`.sqrt()`, products) feeds command production and hence the golden hash, and PLAN §8.2 even keeps a rhai feature-parity gate because rhai config changes evaluation. The committed scenarios (`script-ascent.ron`, the M9a tests, the recorded `flight-launch` log if scripts ever enter it) all execute rhai code inside the hashed run.
**Evidence**: `const TRACKED_DEPS: &[(&str, &str)] = &[("parry3d-f64", ..), ("rapier3d-f64", ..), ("libm", ..), ("rand_chacha", ..), ("blake3", ..)]` — no rhai. PLAN §7.1: the fingerprint exists so a bump is never "an unexplained red build — which is how determinism gates get switched off."
**Impact**: A `rhai` version bump that changes float evaluation order produces `HashMismatch` while `fingerprint_warnings` reports an empty diff — the exact failure mode the sidecar was built to explain, and the one most likely to make an on-call dev blindly rebless.
**Suggestion**: Add `("rhai", "CSP_DEP_VERSION_RHAI")` to `TRACKED_DEPS` and a `rhai: Option<String>` field to `Fingerprint`/`FingerprintSidecar`/`fingerprint_warnings` (goldens rebless once; the schema fields are additive to the sidecar JSON). Consider `bincode` for the same reason — the artifact wire decoder changes across bincode major versions (currently caught only as a `Decode` error).

### [SEVERITY: MEDIUM] Finding 5: dv_used_mps integrates the post-drain throttle across a whole multi-tick advance — wrong exactly when scripts/autopilots change throttle mid-span
**File**: crates/csp-bench/src/agent.rs:417-438 (accumulate_dv)
**Problem**: After each boundary `accumulate_dv(from = tick-1, to = report.reached_tick)` charges `throttle * (thrust/mass) * dt` where `dt` spans the entire advance — including a `step_frame` that ran thousands of ticks on an `AdvanceTo` — using only the *final, post-drain* throttle and mass of each vessel. Any producer that changes throttle mid-span invalidates the integral: a script that burns 100 ticks and cuts (or an autopilot cutoff during warp) is charged the cut throttle for the whole span, and a mid-span *ignition* is charged as if it burned from the start.
**Evidence**: The doc itself hedges: "Reads the *post-drain* throttle (the commanded state for the span — the M2 control surface holds it absolute until re-commanded)" — that claim only holds for commands issued at boundary drains, not for sim-derived commands, which the same file explicitly supports (§2.10 producers re-issue inside the span; `Lockstep::step` re-issues partials without re-polling). `dv_used_mps` is one of the plan's three score axes (§2.12.1: "score (Δv used, sim-time elapsed, funds spent)").
**Impact**: The committed suite happens to step one boundary at a time so its numbers are right, but the API silently mis-scores any `Script`/`Log` scenario that pairs burns with long `AdvanceTo`s — the exact scenarios the eval tier exists to grade. Scores are compared across runs/agents; a wrong axis corrupts that comparison invisibly (determinism tests pass — both runs are wrong identically).
**Suggestion**: Integrate per drained segment: either walk the report's `fired_events`/`script_log` segmentation to find mid-span throttle changes, or (simpler, honest) accumulate inside the loop as `sum over step_frame calls of (throttle_at_call_end * ticks_advanced_this_call)` — re-reading throttle after each partial re-issue narrows the error to one partial frame — and document the residual granularity in the field doc.

### [SEVERITY: MEDIUM] Finding 6: A scenario file with zero goals passes vacuously — the suite is additive-by-file and only one filename is pinned
**File**: crates/csp-bench/src/scenario.rs:384-435 (validate), :699 (pass computation)
**Problem**: `validate()` enforces `goals.len() <= MAX_GOALS` but no minimum, and `goals` is `#[serde(default)]`. The verdict is `let pass = goals.iter().all(|g| g.passed) && agent_faults.is_empty();` — trivially `true` for an empty goal list. `eval::run_suite` picks up every `*.ron` in the directory, and the only anti-vacuous guard in tests/eval_suite.rs is that `ascent-mission.ron` exists.
**Evidence**: A file as small as `(schema_version: 1, name: "x", world: Empty, agent: Idle, tick_budget: 1, event_budget: 1)` parses, runs ~1 boundary, and reports `"pass": true` with `goals: []`; `csp-eval --suite` exits 0 on it. `stop_when` does not help — it is optional and not a verdict.
**Impact**: An eval author (or an agent being graded by scenario-dropping) can green the suite with assertion-free scenarios. `EvalReport.pass` is the number the outside world reads as "the mission succeeded"; an empty assertion set makes it a lie by construction. This matters more as scenarios multiply: today's guard pins exactly one of five files.
**Suggestion**: In `validate()`, reject `goals.is_empty()` ("a scenario with nothing to assert is not a scenario — use csp-replay for pure replays"), or at minimum make `run_suite`/`csp-eval --suite` fail on any suite member with zero goals so the committed directory cannot accumulate vacuous entries.

### [SEVERITY: LOW] Finding 7: `csp-replay record` is an unguarded second golden writer that bypasses every §8.4 anti-laundering refusal
**File**: crates/csp-bench/src/bin/csp-replay.rs:51-68
**Problem**: §8.4's protection chain — refuse on dirty tree, refuse a hash change without a `HASH_SCHEMA_VERSION` bump or `--reason` — lives entirely in `xtask bless-goldens`. The shipped `csp-replay record <scenario> <dir>` writes the same three artifacts directly into the fixture dir with none of those checks. `record`'s self-check only proves the new artifact reproduces *itself*; it says nothing about whether the hash changed from the committed golden.
**Evidence**: `let golden = replay::record(recipe, dir)?; replay::write_golden(dir, &golden)?;` — no comparison against the existing `expected-hash.txt`, no reason flag. `verify_golden`'s doctored-artifact checks don't help: after a `record`-overwrite all three files are freshly consistent, so a determinism regression can be committed as a "golden update" with no trace of the refusal workflow.
**Impact**: The §8.4 gate is procedural, not enforced by the code path most likely to be run by hand. Anyone debugging a red golden who reaches for `csp-replay record` (the primitive the bin's own help advertises) launders the regression silently.
**Suggestion**: Have `csp-replay record` refuse when the target dir holds a full artifact set whose `expected-hash.txt` differs from the new hash unless `--reason` is passed (mirroring xtask), or move the refusal into `replay::write_golden` itself so both writers inherit it.

### [SEVERITY: LOW] Finding 8: perf scenes build the fixture world twice per measurement
**File**: crates/csp-bench/src/perf.rs:644-657, :661-675, :683-694
**Problem**: `measure_atmo_200`, `measure_orbit_1000`, and `measure_landed_300` each call `fixture_world()` (full system + balance + experiments + sites + contracts + recipes load) only to clone the `Environment`, then call `measure_tick_scene` which calls `fixture_world()` again from scratch.
**Evidence**: `let w = fixture_world()?; let env = w.environment().cloned()...; let mut m = measure_tick_scene(... /* which starts with `let mut w = fixture_world()?; */)`
**Impact**: Doubles data-load cost per row and — more subtly — risks the two worlds diverging if the fixture ever changes between the two constructions within one run (it cannot today, so this is waste, not wrongness).
**Suggestion**: Pass the world (or the cloned `Environment`) into `measure_tick_scene` instead of rebuilding it, or add a `measure_tick_scene_on(world, ...)` variant.

## Verdict (honest, 5 lines)
The replay core itself is genuinely strong: strict whole-log entry comparison, final_tick pinning, fixture freeze, doctored-artifact cross-checks, and a record-time self-check — I could not construct a laundering path through `replay()`/`verify_golden()` itself.
The determinism story fails at the edges, not the core: the flagship flight-launch golden is committed and never verified by anything (Finding 1), and the perf tier's budgets are numerically unenforced in every path that actually runs (Finding 2) — the harness records honestly but gates nothing.
The eval tier is well-designed (verdict/error split, lease-gated agents, byte-reproducible deterministic sources) with two real holes: vacuous zero-goal passes (Finding 6) and a Δv score that mis-integrates under mid-advance throttle changes (Finding 5).
The fingerprint is faithful to §7.1's field list but the list itself misses rhai, the one scripted-float dep whose bumps cause unexplained reds (Finding 4); the lockstep transcript's tick bookkeeping is off-by-one against the §7.6 stamps it claims to correlate with (Finding 3).
No fabricated numbers or fake stubs found in what the code claims to do — every measurement is real; the dishonesty lives in what the surrounding automation (or absence of it) lets those measurements get away with.
