### [rest] Finding 1: Warp-up mathematically unreachable on real scenes — CONFIRMED
**Original**: `affordable()` compares ms-per-second (LHS) against ms-per-frame (RHS) — 60x stricter than documented intent; promotion to x2 needs <43 µs/tick vs committed 0.67–4.6 ms/tick.
**Verification**: warp.rs:143-146 reads `measured_step_ms * TICK_HZ * WARP_LADDER[idx] * margin < BUDGET_FRACTION * FRAME_BUDGET_MS`. Independent arithmetic (TICK_HZ=64 confirmed at crates/csp-core/src/time.rs:9; FRAME_BUDGET_MS=1000/60 at warp.rs:39; BUDGET_FRACTION=0.5 at :37):
- LHS units: (ms/tick) x (ticks/s) x multiplier = **ms per wall-second** of sim stepping. `observe`'s input is genuinely per-tick: lib.rs:982-983 computes `last_tick_ms = step_frame_ms / ticks_last_frame().max(1)`.
- RHS: 0.5 x 16.67 = 8.333 **ms per frame** — warp.rs:35-38 says "share of the frame budget" and "(60 fps)". Dimensional mismatch, factor 60.
- Promotion to rung 1 (x2, margin 1.5) requires `measured_step_ms < 8.333/(64x2x1.5) = 0.0434 ms = 43.4 µs/tick`. Rung 2 (x10) needs < 8.7 µs/tick. Rung 0 (x1) demotion threshold is 130 µs/tick.
- Against docs/perf/perf-log-devbox-release.ron (all values re-read): sim.200-part-atmo = 0.6719 ms/tick (LHS 129.0 vs 8.33, **15x over**), sim.1000-part-orbit = 4.6344 (**107x over**), sim.300-part-landed = 0.9986 (**23x over**), even sim.map-500-rails = 0.145 ms/tick (**3x over** the x2 threshold). At 0.67 ms/tick `ladder_ceiling(1.5)` = 0, `margined (0) > next (0)` is false, so `promote_streak` never builds — warp.rs:178-201. `effective` stays 0 (x1) forever.
- Warp.rs's own ladder doc (:10-13) says x3/x4 unlock "when measured per-tick cost … is ≤0.5 ms" — at 0.5 ms/tick the code computes 0.5x64x2x1.5 = 96 > 8.33: the authors' stated operating point cannot promote one rung.
- Test corroboration: `cargo test -p csp-app --lib warp::` passes 9/9 only because every test feeds `observe(0.0, ..)` or `5e-6`/`5e-5` ms/tick — warp.rs:388 uses 5e-6 ms = **5 ns/tick**, mislabeled "5µs" (5 µs = 5e-3 ms would fail every rung: 5e-3x64x1e4x1.5 = 4800 > 8.33).
- Upward-path uniqueness confirmed: `SetWarp` is enqueued only at lib.rs:516 (set_cap — demotion only), :843 (decide — the sole possible upward path), :960 (demote — downward). No other promotion route exists.
- Intent-correct check: with the /60 fix, 0.672 ms/tick at x2 costs 1.43 ms/frame < 8.33 (affordable; even x10 = 7.17 ms passes), while the 1000-part station (9.89 ms/frame at x2) still derates — the fix produces a sane working ladder, confirming the intent reading.
- Impact as stated is accurate: with any real vessel, pressing `.` raises `requested` (HUD shows it via `update_session(requested_multiplier(), multiplier(), ..)`, lib.rs:871-872) but effective warp never leaves x1. HIGH is justified: the headline feature is dead on all committed perf scenes. Suggested fix (divide LHS by 60, equivalently multiply RHS by FPS) is dimensionally correct.

### [rest] Finding 2: settings save is truncate-in-place — CONFIRMED
**Original**: `std::fs::write` truncates the destination; crash/ENOSPC mid-save destroys the previous good settings file.
**Verification**: settings_io.rs:408 — `std::fs::write(path, text).map_err(...)`; no temp file, no rename, no fsync anywhere in the function (401-409). `std::fs::write` opens with O_TRUNC before writing, and on a mid-write failure the error is returned *after* truncation, so even a handled failure has already destroyed the old contents. Callers (`persist_settings` on Apply/close, lib.rs:526+) run the full serialize-then-write with no atomicity. Confirmed MEDIUM.

### [rest] Finding 4: one-shot envelopes truncate mid-decay; EngineCut dives to 20 Hz — CONFIRMED
**Original**: buffers cut at 1.7–3.1τ of their decay envelopes (click on cue tails); EngineCut's falling blip is `sine(f(i), i)` whose instantaneous frequency ends at 20 Hz, not the commented 80.
**Verification**: Envelope end values recomputed independently (`exp(-len/τ)`, synth.rs:80-83, recipes at :156-244): EngineIgnition exp(-0.6/0.35)=**0.180**, Contact exp(-0.3/0.11)=**0.0654**, Breakup noise term exp(-0.9/0.3)=**0.0498** (48 Hz partial at 0.105), UiConfirm exp(-0.09/0.03)=**0.0498** (x0.35 amplitude ≈ 2% step), VesselLeftBubble exp(-0.25/0.09)=**0.0622**, VesselRemoved exp(-0.4/0.13)=**0.0461** — all match the report to 3 decimals. `decay`'s own doc says "gone at ~5τ" (:80); no recipe allocates >1.75τ (EngineIgnition), so every tail is a step discontinuity into silence. EngineCut (:174-176): phase of `sin(2π·f(i)·i/SR)` has instantaneous frequency `f(i) + i·f'(i) = 140 − 120·i/N`, ending at **20 Hz** — the classic chirp mistake (phase must integrate frequency); the comment claims "140 → 80 Hz". Confirmed MEDIUM (audible-click + wrong-pitch, player-visible on every cue).

### [lib1] Finding 1: wasm deferred GPU init drops a resize during the init window — CONFIRMED
**Original**: a `Resized` landing while `self.gpu == None` is recorded only into settings; `finish_gpu_init` sizes everything from spawn-time `gpu.config`; nothing replays the true size — stretched canvas until manual resize.
**Verification**: init chain confirmed: lib.rs:673-682 captures `window.inner_size()` at spawn; `finish_gpu_init` (:714-769) creates `VabRenderer::new`/`FlightRenderer::new` at `(gpu.config.width, gpu.config.height)` (:736-745) and never re-reads `window.inner_size()`. The Resized handler (:2226-2248) records into `settings.graphics.window_size` (:2232-2233) but both `gpu.resize` (:2235-2237) and the renderer resizes (:2242-2247) are `if let Some(gpu)`-guarded, so they are skipped during the window. No pending-size field exists; grep of all `.resize(` sites shows only :1242 (Reconfigure — also stale-dims), :2236/:2243/:2246 (the guarded handler) — no per-frame reconciliation. The in-code mitigation (:876-886) re-feeds only the *camera viewport* from stale `gpu.config`, which keeps the projection consistent with the stale surface but cannot restore the true extent; `Gpu::resize` (csp-render/src/lib.rs:187-193) just reconfigures with passed dims, and the surface config is fixed at spawn (csp-render :163-174). `paint`'s egui `ScreenDescriptor` also uses `gpu.config` (:1249-1252) while `egui_state.take_egui_input(window)` (:866-867) feeds egui the *live* window size — layout and render target disagree, so the stretched-scene/clipped-UI symptom is real. `settings.graphics.window_size` is only re-applied "at the next `init_graphics`" (comment :2227-2228), i.e. next launch. Recovery = user resizes again, as claimed. Confirmed MEDIUM.

### [lib1] Finding 2: unthrottled redraw while occluded/minimized — CONFIRMED
**Original**: no `Occluded` handling; `render()` runs the full sim+egui frame then `paint` skips on `FrameResult::Skip`; redraw re-armed unconditionally — full frame cost per vsync presenting nothing.
**Verification**: lib.rs:788-790 — `self.run_frame(...); self.paint(...); window.request_redraw();` unconditional; second re-arm inside `paint` at :1430; third in `about_to_wait` at :2344-2346. `run_frame` contains the whole step: warp decide + `sim_step` (:899-983) and egui UiBuild via `view.end_frame()` (:987). `paint` tessellates (:1191-1194) and applies the egui texture delta (:1216-1224) *before* `gpu.begin_frame()`, and `FrameResult::Skip => return` (:1245-1246) never touches the redraw schedule. `Skip` provably covers occlusion: csp-render/src/lib.rs:235-241 maps `CurrentSurfaceTexture::Occluded` (and Timeout) to `FrameResult::Skip`. No `WindowEvent::Occluded` arm exists anywhere in lib.rs (grep-verified; the only window-event arms found are Focused/Resized/RedrawRequested etc. at :2202-2333). One nuance: on wasm a *hidden tab* pauses RAF entirely, so "the RAF loop likewise burns the tab" is overstated for the hidden case — but the native occluded/minimized claim (full sim + egui + tessellate + texture upload per vsync, zero presented frames, no idle) is fully confirmed. Confirmed MEDIUM.

### [lib1] Finding 3: Reconfigure recovery reuses stale `gpu.config` dims — CONFIRMED
**Original**: the `FrameResult::Reconfigure` arm reconfigures with the old config size while the authoritative `window` is in scope; a size-change race stays broken until a `Resized` event follows.
**Verification**: lib.rs:1237-1244 — `let (w, h) = (gpu.config.width, gpu.config.height); gpu.resize(w, h); return;` inside `fn paint(&mut self, window: &Window)` (signature :1184 — `window` unused on this path). `Gpu::resize` (csp-render:187-193) only re-applies the passed dims; a surface `Outdated` caused by a window resize whose `Resized` is still queued cannot be satisfied by stale dims, and unlike the Resized handler this path also skips the flight/vab depth-target resizes. Confirmed LOW (worst case a few black frames; fix is one line plus the target resizes).

### [lib2] Finding 2: throttle axis retargets to a new focus vessel with the old vessel's value — CONFIRMED (repro corrected)
**Original**: a throttle key held through a focus change ramps the new focus vessel from the old vessel's commanded axis — silent cross-vessel throttle bleed.
**Verification**: The mechanism is confirmed: `throttle_axis` is rebased from `body.throttle` only on a *fresh* hold (`throttle_press`, lib.rs:1739-1757, `len() == 1`) and by the Z/X snap keys (:1705-1709); `tick_throttle_ramp` (:1793-1821) clears the hold only in read-only/Vab mode — Map mode keeps ramping — and has no focus-identity check; `throttle_axis_step` (:1828-1845) enqueues `SetThrottle { vessel: flight_focus() NOW, throttle: old_axis }`. **One correction to the cited repro**: Tab (`CycleFocus`, settings.rs:551) in map mode changes only the map camera focus (`MapInput.focus_vessel`, csp-view/map.rs:295-311) and does *not* change `flight_focus()` — `FlightUiData.focus` resolves as pin-else-newest-staged (csp-view/flight.rs:1442, :1643-1645), and `FlightFocusOverride` is pinned only by `recover_control` (csp-view/lib.rs:1635). The real triggers are: (a) **RecoverControl (key-t, settings.rs:552)** in map mode while holding Shift — `recover_control` pins flight focus to the recovered vessel (lib.rs:2119-2126 → csp-view/lib.rs:1635), the ToBubble conversion makes it `InBubble` so `throttle_blocker()` (:1667-1680) returns None, and the next frame's ramp enqueues SetThrottle on the *new* vessel from the *old* axis; and (b) the newest-staged fallback — the focused vessel leaving the snapshot (destroyed/staged away) silently moves `vessels.last()` focus onto another craft mid-hold. Both paths log as legitimate player commands in the §7.6 replay. Confirmed MEDIUM with the corrected repro; the suggested fix (track the hold's vessel id, drop-or-rebase on mismatch) stands.
