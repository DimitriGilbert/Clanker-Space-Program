### Finding 1: Burn time silently discarded when a burn ends outside the per-tick shutdown path — CONFIRMED
**Original**: Flight-qualification credit is emitted only by `bubble_part_tick`'s shutdown branch; residence-change restamps and a mid-burn `IgnitionFailure` set `burning=false` without a burns entry.
**Verification**:
- The only emitter of burn credit is reliability.rs:1398-1404 (`engine && rec.burning && throttle <= 0.0` → `out.burns.push(...)`), collected into `rel_burns` at lib.rs:3826 and credited at lib.rs:3915-3932. `TickEffects::burns` has no other producer (grep over reliability.rs).
- `reliability_residence_change(to_dormant=true)` (reliability.rs:773-782) calls `rec.restamp(tick, …, true, false)`; `restamp` (reliability.rs:219-230) sets `self.burning = burning` directly. The function returns `()` — there is no burns output and no caller-side credit. Same pattern in `transition_latched` (lib.rs:9821, `rec.restamp(sim.ticks(), lambda, true, false)`): a landing with throttle still up (suicide-burn touchdown) drops the whole burn.
- Mid-burn `IgnitionFailure`: the in-bubble crossing (reliability.rs:1461-1476) draws from the full mode list while `operating` (burning), and `apply_mode_to_record` (reliability.rs:1261-1264) sets `rec.burning = false; rec.misfire = true;` with no credit. `apply_failure_at`'s twin arm (1052-1056) is dormant-only, so it cannot fire mid-burn — the reachable mid-burn kill is the in-bubble one.
- The common case is worse than reported: an executor-driven maneuver burn ends via `finish_burns` (lib.rs:4196-4243). On the completion tick `drive_node_burn` (lib.rs:8084-8087) sets `body.throttle = dv_remaining/full` (> 0) and returns true; the reliability pass then runs at that positive throttle (lib.rs:3794), so the shutdown branch does not fire. `finish_burns` then zeroes `body.throttle` (4214) and calls `apply_to_rails_at` (4216) → `reliability_residence_change(…, true)` at lib.rs:5397 — the ENTIRE burn's credit is dropped on the standard completion path, not just partial seconds.
- Contradicts the module doc's stated model ("flight units on burn completion (burn duration × a regime-weighted rate)", reliability.rs:76-79). `split_records` (reliability.rs:1522-1540) does carry `burning=true` records verbatim to both halves, so the in-bubble staging/undock parenthetical in the report is accurate.

### Finding 2: `theta = +inf` poison strikes the renewal draws mid-game — CONFIRMED
**Original**: The unguarded `-log(u)` at the two renewal sites shares the fresh-record `U=0` → `+inf` → permanent `Fatal` state-hash fault path; theta is serialized so the save is bricked.
**Verification**:
- csp-core/src/rng.rs:93-96: `uniform = (rng.next_u64() >> 11) as f64 * 2^-53` — returns exactly `0.0` when the top 53 bits are zero. The csp-core claim is verified by construction (range [0,1), inclusive of 0, p = 2^-53 per draw).
- Unguarded renewal draws confirmed: reliability.rs:1046 (`rec.theta += -libm::log(u)` in `apply_failure_at`) and reliability.rs:1260 (same in `apply_mode_to_record`). No `u == 0.0` guard or clamp at either site, nor at `fresh_record` line 414. `log(0.0) = -inf`, so any `U == 0` draw makes theta `+inf` permanently (theta only changes at renewals).
- Hash path: `hash_record` (reliability.rs:565) writes `h.f64(r.theta)` unconditionally; `StateHasher::write_f64` (csp-core/src/hash.rs:318-320) rejects non-finite, `f64` records the fault (296-301) and `finish` surfaces `Fatal`. `hash_vessel_reliability` is inside the per-vessel state-hash walk (lib.rs:10395). Note `dormant_failure_tick` (reliability.rs:522-525) does guard `!rec.theta.is_finite()` — so `fresh_record`'s comment "handled everywhere" (411-413) is already false for the hash walk; the renewal sites extend the same hole.
- Serialization: `PartReliability` derives Serialize/Deserialize (reliability.rs:139) — the poisoned theta persists across save/load (CBOR encodes f64 inf; bincode stores bits).
- Impact nuance (minor overstatement only): `step_frame` does not call `state_hash` internally, so "every tick rolls back" is not the live loop's behavior. But `state_hash` failures are permanent and every consumer is hit: the server backend calls it on every `summary()` and `store_save` (csp-server/src/backend.rs:466,491) — the session can no longer save or even report status — and csp-bench's contract replay (csp-bench/src/contracts.rs:247) fails. Substance confirmed.

### Finding 3: v1 save-migration arm decorative — CONFIRMED (mechanism corrected)
**Original**: `WorldSnapshotV1` aliases live types so genuine v1 bodies can never load; `migrate_v1_to_v2` migrates nothing; in-range stamps that fail the decode proof get a false "outside the chain" message.
**Verification**:
- Live-type aliasing confirmed: save.rs:213 `pub vessels: BTreeMap<VesselId, Vessel>` (live `Vessel` → live `WeldPart`), plus M9b snapshot fields (273-279) aliased from the live `WorldSnapshot`. The module's own version table (save.rs:47-58) states the live serialized tree grew when `WeldPart::engine` was added under the v2 stamp — i.e. genuine first-public-build v1 bodies are pre-`engine`.
- `WeldPart` (csp-phys/src/part.rs) carries `pub engine: Option<EngineSpec>` with no serde attributes on any field — confirmed.
- Mechanism correction (empirically probed with serde 1 + ciborium 0.2.2, the workspace versions): serde does NOT error on the missing `engine` field — a missing `Option` field defaults to `None` (which is exactly the "silent unmetering" the module doc at save.rs:50-52 warns about). The refusal instead comes from the byte-exact re-encode gate in `decode_body`'s `decode` closure (save.rs:612-624): the decoded value re-encodes WITH `engine` present, bytes differ (probe: 12-byte pre-engine body vs 20-byte re-encode), → `TrailingBytes` → mapped to `UnsupportedVersion { found: 1 }` at save.rs:635. Conclusion unchanged: no genuine pre-engine v1 body can load.
- `migrate_v1_to_v2` (save.rs:336-378) is a pure field-wise copy — migrates nothing, synthesizes no defaults. Confirmed.
- Message: save.rs:435-439 renders "save version {found} is outside this build's chain (1..=3)" — for `found: 1`/`found: 2` decode-proof refusals this is factually false (1 and 2 are inside the chain; the schema is unresolvable). Confirmed.
- Circular fixture confirmed: `v1_bytes` (save.rs:730-733) builds v1 artifacts from the CURRENT live snapshot via `From<&WorldSnapshot>`; `v1_save_migrates_to_current` (809-817) and `migrated_save_restores_identical_world` (823-831) both use it. The only "unresolvable v1" test (869-875) feeds `&42u64` — garbage, not a genuine pre-engine body. `cargo test -p csp-sim --lib save::` passes 14/14 as expected.

### Finding 4: Docking a spec'd vessel to a specless craft permanently kills the reliability model for both halves; undock never restores — CONFIRMED
**Original**: `apply_latch` empties the merged spec table unless BOTH halves are `specs_parallel`; the undock/breakup split then clones the empty table to both halves, and no gate ever flags or repairs it.
**Verification**:
- `specs_parallel` (reliability.rs:679-681) is `reliability.len() == parts.len()` — an empty table over a non-empty craft is NOT parallel. The empty table is a legal state: spawn gate lib.rs:5171-5178 ("empty (no model — hand-built test craft)") and restore gate `check_restored_craft` lib.rs:9264-9272 both accept it.
- Merge: joints.rs:917-925 — `reliability_table_m` is `Vec::new()` unless `specs_parallel(&craft_p) && specs_parallel(&craft_s)`. One specless half empties the merged table even when the other half is fully spec'd. Every reader gates on `specs_parallel` (`spec_for` 720-727, `bubble_part_tick` 1341/1351, `reliability_residence_change` 762, `transition_latched` 9810) — the model is fully inert.
- Split propagation: undock retained side lib.rs:6411-6416 (`reliability: craft.reliability.clone()`), fragment lib.rs:6456-6461 (same), and breakup fragment lib.rs:10046 (same) — the degraded empty table is handed verbatim to both halves. The records themselves survive (`split_records`, reliability.rs:1522-1540) and keep hashing (hash_vessel_reliability is unconditional), so nothing observable flags the loss.
- No repair path: grep over csp-sim finds no spec-table re-derivation anywhere — the only writers are spawn (from the command's craft def), the latch merge, and the clone-on-split. One dock/undock cycle with a specless craft is permanent for the session and persists through save/load.
