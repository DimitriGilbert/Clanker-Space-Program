### [MEDIUM] Finding 1: `uniform()` can draw exactly 0.0, and its `-ln U` consumers feed `+inf` straight into the rule-4 hasher
**File**: crates/csp-sim/src/reliability.rs:411-417, :565, :1046, :1260 (primitive: crates/csp-core/src/rng.rs:93-96; trap: crates/csp-core/src/hash.rs:318-326)
**Problem**: `csp_core::uniform` returns `[0, 1)` — including exactly `0.0` when the top 53 bits of the first ChaCha8 word are all zero (p = 2^-53 per draw). Reliability's theta draws do `-libm::log(u)` with no zero guard, and the module comment claims the result is safe: "U = 0 would give +inf — a part that never fails; legitimate (probability ~2^-53) and handled everywhere as 'no crossing inside any horizon'" (reliability.rs:411-413). That claim is false on the hash path: `hash_record` writes `h.f64(r.theta)` raw (reliability.rs:565), and `StateHasher::write_f64` treats `+inf` as a rule-4 `SimError::Fatal` (hash.rs:318-326) — `finish()` then errors.
**Evidence**: `let theta = -libm::log(u);` at reliability.rs:414 (same exposure at :1046 `rec.theta += -libm::log(u);` and :1260); `h.f64(r.theta);` at :565; `if !v.is_finite() { return Err(SimError::Fatal("non-finite f64 in state hash")); }` at hash.rs:319-321. Production hashes state: `csp-server/src/backend.rs:466` and `:491` call `World::state_hash()`, as does every golden/replay harness.
**Impact**: A part whose `{REliability, instance, 0}` (or any renewal) draw lands on 0.0 stores `theta = +inf`, after which every `state_hash()` of the world returns `Fatal` — the tick boundary aborts/rolls back (§2.13), and because the draw is a pure function of `(save_seed, instance, counter)`, reload and rollback deterministically reproduce it: that save is permanently unhashable and unplayable past part creation. Probability per draw is ~2^-53, but the failure is permanent and silent-by-claim (the physics guards at :523 and :1458 do handle `+inf`; only the hash walk does not).
**Suggestion**: Guard the log consumers, not the primitive: `let theta = -libm::log(u.max(f64::MIN_POSITIVE));` at all three sites (reliability.rs:414, :1046, :1260). `u.max(MIN_POSITIVE)` is identity for every `u > 0`, so existing saves/goldens are byte-unchanged; only the currently-fatal 0.0 case maps to a huge-but-finite theta with identical "never crosses any horizon" semantics. Optionally document on `csp_core::uniform` that `[0,1)` includes 0.0 and log/1/x consumers must clamp.

### [MEDIUM] Finding 2: Quaternion double-cover is not canonicalized anywhere — `q` and `-q` hash differently for identical orientations
**File**: crates/csp-core/src/quat.rs (whole module); consumer evidence crates/csp-sim/src/lib.rs:10432-10435
**Problem**: A unit quaternion and its negation encode the same rotation, but the state hash treats them as different states. csp-core canonicalizes `-0.0 -> +0.0` in `write_f64` (hash.rs:322-323) — the exact same class of value-vs-bitpattern problem — yet offers no hemisphere canonicalization for `DQuat`, and the vessel walk hashes the raw components: `h.f64(body.rot.x); ... h.f64(body.rot.w);` (lib.rs:10432-10435).
**Evidence**: `grep -rn canonical crates/csp-core/src/quat.rs` — no canonical-form helper exists; `DQuat::normalize` (quat.rs:95-102) only rescales, never picks a hemisphere. Both signs are stable outputs of the algebra already in the tree: `from_axis_angle(axis, theta)` vs `from_axis_angle(axis, theta - 2*pi)` negate all four components, and the anti-parallel rotation fallbacks choose different axes (csp-sim/src/maneuver.rs:273 vs csp-phys/src/session.rs:814), which flips signs on the same rotation.
**Impact**: No divergence is reachable in the current code — every construction path is bit-deterministic, so same-binary replays agree. The exposure is any future change that computes the same orientation through different algebra (rotation reconstruction, axis fallbacks, refactor of the surface-latch pose round-trip in bubble.rs:206/253): physics-identical worlds then hash differently, goldens/equivalence tests go red for a non-behavioural reason, and the team learns to re-bless — precisely the failure mode the hand-written walk exists to prevent (hash.rs:4-8). Honest caveat: this is a hardening gap, not a demonstrated bug; PLAN §7.1 does not currently mandate it.
**Suggestion**: Add `DQuat::canonical_hemisphere(self) -> Self` (negate if `w < 0.0`, tie-break `w == 0.0` on the first nonzero of `x, y, z`) and apply it where `rot` enters the stream (one line in the lib.rs:10432 walk), landing as a deliberate `HASH_SCHEMA_VERSION` bump + golden rebless. Doing it now, while only a handful of walks hash quaternions, costs one rebless; doing it after more pose records accrete costs the same plus archaeology.

### [MEDIUM] Finding 3: clippy `disallowed-methods` ban list is incomplete (no `f32::` at all, several `f64::` transcendentals missing) and copy-pasted verbatim into four crates
**File**: crates/csp-core/clippy.toml:3-13 (identical copies: crates/csp-sim/clippy.toml, crates/csp-phys/clippy.toml, crates/csp-data/clippy.toml)
**Problem**: The lint is the mechanical enforcement of PLAN §8.2 ("f64 transcendentals are not bit-identical across platforms — libm only" — the file's own header), but the list bans only 15 `f64` methods. Missing: `f64::{sin_cos, exp2, exp_m1, ln_1p, sinh, cosh, tanh, asinh, acosh, atanh}` and every `f32` intrinsic (`f32::sin`, `f32::sqrt`, `f32::powf`, ...). An `f32::tanh` or `.sin_cos()` in csp-phys passes clippy today while violating the same cross-platform rule the list exists to enforce; f32 paths are doubly dangerous because §8.4 fingerprints compare native vs wasm, where a stray f32 intrinsic is exactly the class of divergence that only shows up cross-target.
**Evidence**: Full text of all four clippy.toml files compared — byte-identical ban lists (verified with cat/grep); repo-wide grep for the missing functions (`.sin_cos(|.exp2(|.tanh(|...` and `f32::(sin|sqrt|powf|exp|ln|...)`) over crates/{csp-core,csp-sim,csp-phys,csp-data} returns zero hits, so this is an enforcement hole, not an active violation.
**Impact**: No current bug — zero uses. The risk is structural: the determinism domain's source-level gate has holes, and the same incomplete list is maintained in four places, so fixing one file silently leaves three stale (no check keeps them in sync).
**Suggestion**: Complete the list (`f64::{sin_cos, exp2, exp_m1, ln_1p, sinh, cosh, tanh, asinh, acosh, atanh}` plus `f32::` mirrors of every entry) in all four files, and add a sync assertion to the existing `xtask lint-deps` (or a plain byte-equality check of the four clippy.toml files) so the copies cannot drift.

### [LOW] Finding 4: the load-bearing `[0,1)` scaling expression exists twice — `rng::uniform` in csp-core and a hand-rolled `next01` in csp-sim
**File**: crates/csp-sim/src/contracts.rs:231-233; primitive at crates/csp-core/src/rng.rs:93-96
**Problem**: csp-core offers only the one-shot `uniform(save_seed, key)` (re-seeds, draws once). Consumers that legitimately need several draws from one seeded stream must hand-roll the scaling — and contracts.rs did: `fn next01(rng: &mut impl Rng) -> f64 { (rng.next_u64() >> 11) as f64 * (1.0 / (1u64 << 53) as f64) }` is character-for-character the body of `rng::uniform` minus the KDF. The shift width (11), the 53-bit precision, and the 2^-53 scale are determinism-critical constants with golden-pinned behavior in csp-core only.
**Evidence**: rng.rs:95 `(rng.next_u64() >> 11) as f64 * (1.0 / (1u64 << 53) as f64)` vs contracts.rs:232 identical expression. Grep shows no other in-tree duplicates (reliability always uses the one-shot `uniform`).
**Impact**: Maintainability exposure: a future "improve precision / avoid 0.0" change to `rng::uniform` (see Finding 1) would not propagate to `next01`, leaving contract offers on the old scale — caught only after the fact by goldens, and only if a scenario exercises that path. Also `next01`'s zero-return feeds `pick` and weighted choice, which tolerate 0.0, so no active bug.
**Suggestion**: Add `pub fn uniform01(rng: &mut impl Rng) -> f64` to csp-core (the stream-position draw, KDF-free), implement both `uniform` and the new entry point in terms of it, and make `contracts::next01` a call into it. No behavior change, no golden churn.

### [LOW] Finding 5: `HASH_SCHEMA_VERSION` changelog documents v13 before v12, inverting the audit trail's order
**File**: crates/csp-core/src/hash.rs:108-119
**Problem**: The version-history comment block (the crate's coordination ledger for golden reblesses) lists "**Version 13** (M7-C)" at line 108 and "**Version 12** (M7-B)" at line 116 — out of chronological order. The constant itself (`= 20`, line 200) and the bump discipline are correct; only the narrative order is wrong.
**Evidence**: Lines 108-119 read v13 (M7-C, economy) then v12 (M7-B, tech record); every other entry ascends.
**Impact**: Documentation only — but this block is the reference for "which version owned which field", and misreading 12/13 ordering misattributes which walk additions shipped under which bump during incident archaeology.
**Suggestion**: Swap the two paragraphs in the same commit as the next version bump (no code change, no rebless).

## Verdict (5 lines)

1. hash.rs implements PLAN §7.1 rules 1-8 faithfully: LE fixed widths, -0.0 canonicalization, NaN/inf fault-to-`finish`, u32 lengths everywhere (no usize-width divergence), BTreeMap-only, arena ID-sort with duplicate faults — I verified each against the plan text and found no deviation.
2. rng.rs is pinned end-to-end (workspace pins = golden provenance =1.8.3/=0.10.0/=0.10.1), preimage layout is spec-literal, and I audited every StreamKey consumer: no substream collisions exist (Reliability counters 0..n and 1<<63|idx, Ignition by index, Contracts entity-0/offer-index, Generation unused).
3. quat.rs/vec3.rs check out against the standard Hamilton/cross/dot formulas, libm discipline holds (grep: zero non-libm float intrinsics in all four determinism crates), and the no-FMA stance is honestly documented as codegen-reliance with bit-exact canaries.
4. All five findings are edge/lifecycle gaps, not logic errors: two MEDIUMs are a 2^-53-permanent Fatal (with a falsified in-code safety claim) and the quaternion-hemisphere gap; the clippy-list hole is unexploited today.
5. No CRITICAL/HIGH: nothing in this cluster breaks a replay, save, or hash in any reachable scenario on current code — quality is genuinely high; ship after the Finding 1 clamp (one line, zero golden churn).
